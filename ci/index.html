CrowdVision’s CI runs on GitHub Actions. It checks every pull request into master, then publishes images, coverage and the docs site after the merge. Every workflow reads one file to know the services: .github/services.json.

Related pages: Release Please, Dependencies & Security.

Which legs run

A leg runs when its own dir changed, or a folder in its depends_on changed. Every service leg’s condition is just its own key; the dependencies live in .github/services.json, not in ci-gate.yml.

depends_on cannot drift from the code. Before printing the filters, scripts/service-filters.py fails the changes job when:

  • a depends_on folder does not exist, for example after a rename;
  • a go.mod replace ... => ../path or a Cargo.toml path = "../path" points outside the service at a folder no depends_on covers.

A listed service passes its own service dirs on: tenancy lists auth-middleware, so it is also selected by auth-contracts. Plain folders do not pass on: auth-contracts’ fixtures feed its own tests, not the code its consumers compile.

Why: a dependency bump in auth-middleware once passed its own leg, skipped tenancy and claims-gateway, and left both unbuildable on master (missing go.sum entry), unnoticed until a later run rebuilt every service. The hand-written conditions it slipped through had four more holes of the same kind.

Why one gate job

ci-passed waits for every leg with if: always(), so it runs even when legs are skipped.

RuleWhy
changes must be successIf it failed, every leg was skipped without being judged. Green there would be a lie
Every other result must be success or skippedA list of good results, not of bad ones: cancelled or any new value fails too
Only CI Passed is requiredThe ruleset names one check, so adding or removing a leg never touches GitHub settings

A leg nobody waits for passes silently

needs: cannot be computed, so every service job is written three times in ci-gate.yml: as a job, in docker.needs, in ci-passed.needs. A job missing from a list still runs, but the gate goes green without it. scripts/check-workflow-registry.py, run by the workflows-lint leg and by just lint workflows (also before just lint all and just lint affected), compares the three lists with services.json and fails on any gap.

Images on a pull request

ci-docker.yml runs after the legs, once per changed image, when no leg failed.

  • Every image builds from its own Dockerfile, with the same context cd-registry uses: cd_context and dockerfile from services.json, else the service folder and its Dockerfile.
  • The rust-base job runs only when a Rust image is in the matrix. The build job runs when it succeeded or was skipped.
  • if: !cancelled() && !contains(needs.*.result, 'failure') on the gate’s docker job: a skipped leg in needs would otherwise skip it too, and some leg is skipped on nearly every PR.
  • Every image except Go and Rust builds with no-cache, so the apk upgrade / apt upgrade in its Dockerfile runs every time instead of reusing an old layer. Go and Rust ship distroless, with no upgrade step.

A merge, through to published images

StepDetail
3workflow_dispatch with service: all or a list such as twin,frontend. A change to services.json or cd-registry.yml selects every image
5Tag = rust pin from .mise.toml + first 12 characters of the sha256 of docker/rust-base/Dockerfile. An unchanged base is never rebuilt
8A squash merge makes a new commit, so the PR’s head SHA is looked up through the API
10Same Trivy settings as on the PR; the result also goes to the Security tab
11A carbon copy: latest, the SHA and pr-HEADSHA end up on one registry version, the very image scanned on the PR
12Fails the job if latest points at a manifest that is gone
15Happens on a manual run, or when the PR image is missing. frontend gets VITE_VAPID_PUBLIC_KEY as a build arg

Never delete the pr version after promoting it

A promotion that wrote a new index would borrow the pr-HEADSHA version’s manifests. Deleting that version then left latest pointing at nothing: docker pull fails with manifests/sha256:… not found. That is why the copy is exact and no step deletes the pr tag. maint-cleanup.yml uses dataaxiom/ghcr-cleanup-action, which keeps every manifest a kept tag still needs.

Coverage after a merge

cd-coverage.yml measures coverage on master only. Pull requests never measure it, and no threshold blocks anything.

  1. load-registry path-filters the push and splits the changed services by lang into four lists.
  2. One tpl-<lang>-coverage.yml call per non-empty list. An empty list skips the job: GitHub fails a reusable workflow called with an empty matrix.
  3. publish downloads the reports and fetches the previous coverage-counts.json and reports/ from branch coverage-data.
  4. scripts/coverage-summary.py merges new counts over the old ones and rewrites reports/<service>.json for the services that ran, so unchanged services keep their numbers and their per-file report.
  5. The result, badge.json, summary.json, coverage-counts.json and reports/, is force-pushed as a single commit to coverage-data, with 3 attempts.

Example. A push changes telemetry only. rust gets one entry, node, python, go are skipped. The badge is recomputed from the new telemetry counts plus last run’s counts for every other service.

What blocks a merge into master

From the repository rulesets:

RuleValue
Required checkCI Passed, up to date with master
Code scanningCodeQL: security alerts high or higher, or any error-level alert
Merge methodSquash only, linear history
ReviewsA pull request is required; 0 approvals
BranchNo deletion, no force push

Traps

  • tpl-node-ci.yml and .github/actions/filter-languages are unused. No workflow calls them.
  • govulncheck never blocks. Its step has continue-on-error: true.
  • .trivyignore waivers expire. Any fixable HIGH or CRITICAL OS finding fails the image job; a waiver is a line there with its reason and an exp: date, so the job fails again when the date passes.
  • Distroless lags Debian. Go and Rust images run on gcr.io/distroless/*-debian12, which has no package manager: a Debian fix reaches the image only when Google rebuilds the base.
  • SARIF output ignores severity unless told otherwise. trivy-action with format: sarif reports every severity, so cd-registry.yml sets limit-severities-for-sarif: true; without it an UNKNOWN finding fails the job.
  • A Trivy finding can appear with no code change. The scan reads today’s advisory database, so an old base image can fail tomorrow.
  • The gate does not run on a push to master. Only on pull requests. cd-* workflows assume the PR already passed.
