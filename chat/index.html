chat is a Rust service (Axum, MongoDB) in backend/chat. It does four things:

  1. Stores conversations. Each one belongs to one account.
  2. Sends each question to agent, together with the recent history.
  3. Relays the answer to the browser as it is written, token by token.
  4. Saves the exchange once the answer is whole.

agent stores nothing: every /ask stands alone. chat is the part that remembers.

Role in the system: Chat. The other side of the stream: Agent.

The idea in one minute

Think of a receptionist who takes written questions for an expert in the next room.

  • The receptionist keeps a folder per visitor, with every question and answer so far.
  • A visitor writes a question. The receptionist walks to the expert with the question and the last few pages of the folder, so the expert knows what was said before.
  • The expert answers word by word. The receptionist reads each word out loud to the visitor at once, without waiting for the end.
  • Only when the expert says “that is my full answer” does the receptionist put both pages in the folder. If the expert stops halfway, nothing is filed.
  • A visitor can only ever open their own folder. Another visitor’s folder looks like it does not exist.

domain/conversation.rs: the rules, with no framework

The limits

pub const MAX_MESSAGES: usize = 100;
pub const MAX_MESSAGE_LENGTH: usize = 8000;
pub const MAX_TITLE_LENGTH: usize = 120;
pub const DEFAULT_TITLE: &str = "New chat";

A conversation holds at most 100 messages. A question is at most 8000 characters, a title at most 120. A conversation made without a title is called New chat.

The shapes

pub struct Citation {

Checking a text

pub fn validate_text(
    value: Option<&str>,
    name: &str,
    max_length: usize,
) -> Result<String, DomainError> {
    let text = value
        .map(str::trim)
        .filter(|t| !t.is_empty())
        .ok_or_else(|| DomainError::Validation(format!("{name} must be a non-empty string")))?;

    if text.chars().count() > max_length {
        return Err(DomainError::Validation(format!(
            "{name} cannot exceed {max_length} characters"
        )));
    }
    Ok(text.to_string())
}
  1. Trim the spaces. Missing, or empty after trimming: "{name} must be a non-empty string".
  2. Count the characters (not bytes) of the trimmed text. Too long: "{name} cannot exceed {max} characters".
  3. Return the trimmed text.

Trimming first matters: trailing spaces never push a valid question over the limit.

Example. " Why is room 2 hot? " becomes "Why is room 2 hot?", 18 characters, fine.

Three small rules on a conversation

impl Conversation {
    pub fn has_room_for_exchange(&self) -> bool {
        self.messages.len() + 2 <= MAX_MESSAGES
    }

    pub fn recent_history(&self, limit: usize) -> Vec<HistoryTurn> {
        self.messages
            .iter()
            .skip(self.messages.len().saturating_sub(limit))
            .map(|m| HistoryTurn { role: m.role, content: m.content.clone() })
            .collect()
    }

    pub fn title_from_first_question(&self, question: &str) -> Option<String> {
        if self.title != DEFAULT_TITLE || !self.messages.is_empty() {
            return None;
        }
        Some(question.chars().take(MAX_TITLE_LENGTH).collect())
    }
}
  • Room. One exchange adds two messages, so the check is len + 2 <= 100. A conversation with 98 messages is allowed one more exchange (it ends at 100). With 100, the next is refused.
  • History. Skip all but the last limit messages, and send only role and content. With 14 messages and a limit of 10, it skips the first 4 and sends messages 5 to 14. Citations are not sent.
  • Title. Only the first exchange of a conversation still called New chat gets a new title: the first 120 characters of the question. Any later exchange leaves the title alone, so a rename is never overwritten.

The title field has three states

pub enum TitleField<'a> {
    Absent,
    Present(Option<&'a str>),
}

A body without title is not the same as a body with "title": null. The first means “use the default”. The second is an error.

BodyResult
{}Title New chat
{"title":"Floor 3"}Title Floor 3, trimmed
{"title":null} or {"title":" "}400 title must be a non-empty string

A typed Option<String> field cannot tell “absent” from “null” (both become None), so the handler keeps the body as raw JSON and decides itself.

Everything the service may ask the storage. Look at the names: find_owned, delete_owned. Every method takes the user_id. There is no “find by id alone”, so forgetting the ownership check is not possible. Option means “not found” and is not an error.

pub enum AgentEvent {
    Token(String),
    Done {
        answer: Option<String>,
        citations: Vec<Citation>,
    },
}

pub type AnswerStream = Pin<Box<dyn Stream<Item = anyhow::Result<AgentEvent>> + Send>>;

#[async_trait]
pub trait AgentClient: Send + Sync {
    async fn ask(&self, question: &str, history: &[HistoryTurn], claims_header: &str)
        -> Result<AnswerStream, DomainError>;
}

What agent can say: a Token, or Done. answer is an Option because an older agent may not send it. ask resolves as soon as agent has accepted the question and the headers are in. Every later token arrives on the stream. So “could not reach agent” and "agent said 500” are errors of ask, before anything is streamed.

service/conversations.rs: the use cases

The simple ones just add the owner check and the validation:

pub async fn open(&self, user_id: &str, id: &str) -> Result<Conversation, DomainError> {
    self.store
        .find_owned(user_id, id)
        .await?
        .ok_or_else(DomainError::not_found)
}

A miss is NotFound. rename validates the title first, then calls the store. delete turns “deleted nothing” into NotFound. create picks the default title or validates the given one.

send_message: before the first token

pub async fn send_message(
    &self,
    user_id: &str,
    conversation_id: &str,
    content: Option<&str>,
    claims_header: &str,
) -> Result<impl Stream<Item = Result<ChatEvent, DomainError>> + Send + use<>, DomainError>
{
    let question = validate_text(content, "content", MAX_MESSAGE_LENGTH)?;
    let conversation = self.open(user_id, conversation_id).await?;

    if !conversation.has_room_for_exchange() {
        return Err(DomainError::Conflict("Conversation message limit reached".to_string()));
    }

    let history = conversation.recent_history(self.history_limit);
    let upstream = self.agent.ask(&question, &history, claims_header).await?;
    // … build and return the stream

The order is on purpose, cheapest check first:

  1. Validate the text. A bad request costs no database read.
  2. Load the owned conversation. Not found (or someone else’s): NotFound.
  3. Check the room. Full: Conflict (409), and agent is never called.
  4. Build the history and ask agent, forwarding the caller’s own claims header.

Every failure up to here is the outer Err, so the HTTP layer can still answer with a normal status code. The answer has not started.

The return type says it: Result<Stream<…>, DomainError>. The outer Result is “before the first token”. The items inside the stream are “after”.

The stream: Exchange

struct Exchange {
    upstream: AnswerStream,
    answer: Answer,
    finished: bool,
}

struct Answer {
    store: Arc<dyn ConversationStore>,
    user_id: String,
    conversation_id: String,
    question: String,
    new_title: Option<String>,
    text: String,
}

The state of one answer in progress: the stream from agent, the text so far (text), and what is needed to save at the end. They are two structs because the upstream stream is Send but not Sync, so nothing borrowed across an await can live inside it.

async fn step(mut self) -> Option<(Result<ChatEvent, DomainError>, Self)> {
    if self.finished {
        return None;
    }

    match self.upstream.next().await {
        Some(Ok(AgentEvent::Token(text))) => {
            self.answer.text.push_str(&text);
            Some((Ok(ChatEvent::Token(text)), self))
        }
        Some(Ok(AgentEvent::Done { answer, citations })) => {
            self.finished = true;
            if let Some(answer) = answer {
                self.answer.text = answer;
            }
            let persisted = self.answer.persist(citations).await.map(ChatEvent::Done);
            Some((persisted, self))
        }
        Some(Err(_)) => {
            self.finished = true;
            Some((Err(DomainError::BadGateway("agent stream ended unexpectedly".to_string())), self))
        }
        None => {
            self.finished = true;
            Some((Err(DomainError::BadGateway("agent returned an invalid response".to_string())), self))
        }
    }
}

futures::stream::unfold calls step again and again. Each call waits for the next event from agent and produces one event for the browser:

agent giveschat does
Token(text)Add the text to the answer kept in memory. Pass the token on
Done {answer, citations}Stop. If answer is there, it replaces the joined tokens. Save the exchange. Pass on the stored message
An unreadable frame, or a broken connectionStop with agent stream ended unexpectedly
The stream ends with no DoneStop with agent returned an invalid response

Why does answer win? agent can rewrite what the model wrote: it removes citation marks it cannot back, or text streamed before a tool call. The tokens the browser saw may have those; the stored answer should not. An agent that sends no answer gets the joined tokens stored.

The last row is the key one. Done is the only signal that the answer is whole. Without it there is nothing safe to save.

Saving

async fn persist(&self, citations: Vec<Citation>) -> Result<ChatMessage, DomainError> {
    self.store
        .append_exchange(
            &self.user_id,
            &self.conversation_id,
            NewMessage { role: Role::User, content: self.question.clone(), citations: None },
            NewMessage { role: Role::Assistant, content: self.text.clone(), citations: Some(citations) },
            self.new_title.as_deref(),
        )
        .await?
        .ok_or_else(DomainError::not_found)
}

Both halves, plus the new title if there is one, go in one store call. Nothing is written before this. If the conversation was deleted meanwhile, the store returns None and the browser gets a Conversation not found error frame.

adapters/driven/agent.rs: talking to agent

The request

const CONNECT_TIMEOUT: Duration = Duration::from_secs(5);
const READ_TIMEOUT: Duration = Duration::from_secs(60);

client: reqwest::Client::builder()
    .connect_timeout(CONNECT_TIMEOUT)
    .read_timeout(READ_TIMEOUT)
    .build()

Two timeouts, and no total timeout. A total timeout would kill a long answer in the middle. The connect timeout (5 s) bounds the handshake. The read timeout (60 s) applies to each wait for the next bytes, not to the whole response, so it still ends a stream that goes silent but lets a slow, steady answer run for minutes.

let response = self

Turning bytes into events

Bytes arrive in pieces that do not line up with frames. One frame can come in two reads, and one read can hold three frames. This part of the file solves that.

fn take_frames(buffer: &mut Vec<u8>) -> Vec<Vec<u8>> {
    let mut frames = Vec::new();
    while let Some(end) = buffer
        .windows(2)
        .position(|w| w == b"\n\n")
        .map(|start| start + 2)
    {
        frames.push(buffer.drain(..end).collect());
    }
    frames
}

An SSE frame ends with a blank line (\n\n). Look for it in the buffer. Each time one is found, cut everything up to and including it as a whole frame (drain). Whatever is left stays in the buffer, waiting for more bytes. The buffer is bytes, not text, until the cut: a character like ° takes 2 bytes, and cutting text in the middle of it would break it.

fn parse_frame(raw: &[u8]) -> Option<anyhow::Result<AgentEvent>> {
    let text = String::from_utf8_lossy(raw);
    let payload: String = text
        .lines()
        .filter_map(|line| line.strip_prefix("data:"))
        .map(|value| value.strip_prefix(' ').unwrap_or(value))
        .collect::<Vec<_>>()
        .join("\n");

    if payload.trim().is_empty() {
        return None;
    }

    match serde_json::from_str::<AgentFrame>(&payload) {
        Ok(AgentFrame::Token { text }) => Some(Ok(AgentEvent::Token(text))),
        Ok(AgentFrame::Done { answer, citations }) => Some(Ok(AgentEvent::Done { answer, citations })),
        Ok(AgentFrame::Ignored) => None,
        Err(e) => Some(Err(anyhow::anyhow!("unreadable agent frame: {e}"))),
    }
}

Read one whole frame:

  1. Keep only the lines that start with data:, drop the optional space after the colon, join them with newlines. A comment line like : ping has no data:, so it vanishes.
  2. Nothing left: skip (None).
  3. Read the JSON by its type.
#[derive(Deserialize)]
#[serde(tag = "type", rename_all = "lowercase")]
enum AgentFrame {
    Token { #[serde(default)] text: String },
    Done { #[serde(default)] answer: Option<String>, #[serde(default)] citations: Vec<Citation> },
    #[serde(other)]
    Ignored,
}
FrameResult
{"type":"token","text":"…"}Token. A missing text is empty
{"type":"done","answer":"…","citations":[…]}Done. Both fields are optional
Any other typeSkipped (Ignored), so agent can add a new kind of frame without breaking chat
A comment like : ping, or an empty frameSkipped
Not JSONAn error. The exchange ends with agent stream ended unexpectedly

The frames are pinned in schemas/fixtures/agent-stream.json. Its tolerated cases must be survived, so the skipping is a decision, not luck.

async fn step(mut self) -> Option<(anyhow::Result<AgentEvent>, Self)> {
    loop {
        if let Some(event) = self.pending.pop_front() {
            return Some((event, self));
        }
        if self.exhausted {
            return None;
        }

        match self.bytes.next().await {
            Some(Ok(chunk)) => {
                self.buffer.extend_from_slice(&chunk);
                for frame in take_frames(&mut self.buffer) {
                    self.pending.extend(parse_frame(&frame));
                }
            }
            Some(Err(e)) => {
                self.exhausted = true;
                self.pending.push_back(Err(anyhow::Error::new(e)));
            }
            None => self.exhausted = true,
        }
    }
}

The reader works in a loop:

  1. Anything waiting in pending? Hand out the first one.
  2. Exhausted and nothing pending? The stream is over.
  3. Otherwise read the next chunk of bytes, add them to the buffer, cut whole frames, parse each one into pending, and go around again.

A read error becomes an error event, then the stream ends. A clean end of the bytes just ends the stream, and the service above reads the absence of Done as an invalid response.

Example, a split frame. Read 1 brings data: {"type":"token","te. Read 2 brings xt":"Room "}\n\n. After read 1 there is no blank line, so nothing is cut and the bytes wait. After read 2 the whole frame is cut and gives Token("Room ").

Hiding ObjectId

impl From<ConversationDocument> for Conversation {
    fn from(document: ConversationDocument) -> Self {
        Conversation {
            id: document.id.to_hex(),
            user_id: document.user_id,
            title: document.title,
            messages: document.messages.into_iter().map(ChatMessage::from).collect(),
            created_at: iso8601(document.created_at.timestamp_millis()),
            updated_at: iso8601(document.updated_at.timestamp_millis()),
        }
    }
}

Three private “document” types mirror what MongoDB stores (ObjectId, DateTime). Each converts into a domain type: every ObjectId becomes a bare hex string, and every date becomes 2026-11-02T10:15:30.123Z (the JavaScript ISO shape, so the browser contract did not change). This is the only file that knows ObjectId.

Owned lookups

fn owned(user_id: &str, id: &str) -> Option<mongodb::bson::Document> {
    ObjectId::parse_str(id)
        .ok()
        .map(|id| doc! { "_id": { "$eq": id }, "userId": { "$eq": user_id } })
}

Every query on one conversation filters on _id and userId together. Two details:

  • A text that is not a valid ObjectId can never match anything, so it returns None, which the service turns into a 404. It is a miss, not a 400.
  • $eq wraps both values, so a value that looks like a query operator (for example {"$ne": ...}) is treated as plain data. This stops query injection.

Someone else’s conversation is also a miss, so the answer is 404 Conversation not found, never 403. A 403 would tell a stranger that the id exists.

Saving an exchange

let mut set = doc! { "updatedAt": now };
if let Some(title) = new_title {
    set.insert("title", title);
}

let outcome = self
    .collection
    .update_one(
        filter,
        doc! {
            "$push": { "messages": { "$each": [to_bson(&user)?, to_bson(&assistant)?] } },
            "$set": set,
        },
    )
    .await?;

match outcome.matched_count {
    0 => Ok(None),
    _ => Ok(Some(assistant.into())),
}

One update_one does it all: $push with $each appends both messages, $set updates updatedAt and, on the first exchange, title. Two sends at the same moment cannot lose each other’s messages, because each $push is applied atomically by MongoDB. updatedAt is set by hand: the list sorts by it, so a write that forgets it would stop the list reordering, with no error. No match (the conversation is gone): None. The user and assistant messages get the same createdAt.

Every request goes through two layers: a rate limiter and a metrics layer. The limiter allows 300 requests per minute per client IP, then answers 429. The IP is the rightmost value of x-forwarded-for, the one the edge appended, not one the client could write. A sweep once per minute drops the clients that were idle. (The same file is copied into chat, digital-twin and notification: no shared Rust library holds middleware, so a fix in one copy must be made in all three.)

Who is the owner

impl<S: Send + Sync> FromRequestParts<S> for GatewayClaims {
    type Rejection = DomainError;

    async fn from_request_parts(parts: &mut Parts, _state: &S) -> Result<Self, Self::Rejection> {
        let raw = parts.headers.get(CLAIMS_HEADER)
            .and_then(|header| header.to_str().ok())
            .filter(|raw| !raw.is_empty())
            .ok_or_else(|| unauthorized("Missing authentication token"))?
            .to_string();

        let decoded = decode_claims_header(&raw)
            .ok_or_else(|| unauthorized("Invalid authentication token"))?;
        let payload: ClaimsPayload = serde_json::from_slice(&decoded)
            .map_err(|_| unauthorized("Invalid authentication token"))?;

        let user_id = payload.user_id()
            .ok_or_else(|| unauthorized("Authentication token is missing an account id"))?
            .to_string();

        Ok(GatewayClaims { user_id, raw })
    }
}

An Axum extractor, run before any handler that lists claims: GatewayClaims:

  1. No header, or empty: 401 Missing authentication token.
  2. Not base64 JSON (any of the four base64 alphabets is accepted): 401 Invalid authentication token.
  3. No sub, or blank: 401 Authentication token is missing an account id.
  4. Otherwise user_id = sub. The raw header is kept too, to forward to agent.

Errors have one name

impl DomainError {
    pub fn describe(&self) -> (StatusCode, &'static str, String) {
        match self {
            DomainError::Validation(m) => (StatusCode::BAD_REQUEST, "Validation Error", m.clone()),
            DomainError::Unauthorized(m) => (StatusCode::UNAUTHORIZED, "Unauthorized Error", m.clone()),
            DomainError::NotFound(m) => (StatusCode::NOT_FOUND, "Not Found Error", m.clone()),
            DomainError::Conflict(m) => (StatusCode::CONFLICT, "Conflict Error", m.clone()),
            DomainError::BadGateway(m) => (StatusCode::BAD_GATEWAY, "Bad Gateway Error", m.clone()),
            DomainError::Internal(e) => {
                log::error!("{e:?}");
                (StatusCode::INTERNAL_SERVER_ERROR, "Internal Server Error", INTERNAL_MESSAGE.to_string())
            }
        }
    }
}

The streaming handler

fn frame(event: Result<ChatEvent, DomainError>) -> Event {
    let body = match event {
        Ok(ChatEvent::Token(text)) => json!({ "type": "token", "text": text }),
        Ok(ChatEvent::Done(message)) => json!({ "type": "done", "message": message }),
        Err(error) => {
            let (_, error_type, message) = error.describe();
            json!({ "type": "error", "error": error_type, "message": message })
        }
    };
    Event::default().json_data(body).unwrap_or_else(|_| {
        Event::default().data(r#"{"type":"error","error":"Internal Server Error"}"#)
    })
}

pub async fn send_message(
    State(state): State<AppState>,
    claims: GatewayClaims,
    Path(id): Path<String>,
    body: Result<Json<Value>, JsonRejection>,
) -> Result<Sse<impl Stream<Item = Result<Event, Infallible>>>, DomainError> {
    let request = payload(body);
    let events = state
        .conversations
        .send_message(&claims.user_id, &id, text(&request, "content"), &claims.raw)
        .await?;

    Ok(Sse::new(events.map(|event| Ok(frame(event)))).keep_alive(KeepAlive::default()))
}
  • frame turns each event into one SSE frame: token, done (with the stored message) or error.
  • send_message first does .await?. A failure there is the ordinary DomainError, answered with a normal status code.
  • Only then does it return Sse::new(…), and the 200 plus the stream begin. From that moment a failure can only be an error frame, because the status line is already sent.
  • keep_alive makes Axum send a comment line while the stream is quiet, so proxies do not close it.

If the browser goes away, Axum stops reading the stream and drops it. Done is then never reached, so nothing is saved.

Read once at start. The old Node service re-read and re-checked it on every request, so a bad value only showed up as a 500 on the first message. Now the same mistake is a container that refuses to start. Not set: 10. Set to 0, to a negative number or to text: panic.

Gaps

  • Sends to one conversation are not serialised. Two questions sent at the same moment each read the same history and both get stored. Only the frontend, which waits for one answer before the next, prevents it.
  • The cap is checked before the answer, not at the write. Two sends at 98 messages can both pass and leave 102.
  • Rate limiting counts every request. /health and /metrics go through the same 300 per minute per IP, and many people behind one address share one counter.
  • A closed tab loses the answer. Nothing is saved until done, and agent has already done the work.
