Telemetry Service Architecture

Bounded context: Telemetry Ingestion · Stack: Rust / Axum / Postgres + TimescaleDB · Code-level walkthrough: Telemetry Service

The telemetry-service realises the Telemetry Ingestion context. It is the platform’s ingestion gateway, and its architecture answers two independent pressures: absorbing new sensor types without touching the core, and keeping every I/O technology out of the logic that decides what a reading means.

Architectural Style

Hexagonal (ports & adapters) and microkernel on orthogonal axes. They are not competing patterns here; each governs a different direction of change.

AxisPatternVaries
Outward — infrastructurePorts & adaptersPostgres, Redis, Kafka, twin-service, physical devices
Inward — domainMicrokernelwhich metrics exist, what they validate, which bounds they carry

The Node predecessor had the microkernel half only. Its modules owned their own persistence and Redis calls, so infrastructure reached into every metric implementation.

Layers

DirectoryHoldsMay import
src/contracts/pure types, SensorPlugin and ActionSpec, threshold and query rulesnothing
src/kernel/use cases over Arc<dyn Port> — the microkernelcontracts
src/plugins/one file per metric, each a SensorPlugincontracts
src/adapters/Postgres, Redis, Kafka, HTTP in and outeverything

The kernel never names a plugin. Every metric-specific decision is reached through a &dyn SensorPlugin resolved from PluginRegistry, so a new metric is a new file plus one registration line in main.rs.

tests/architecture.rs enforces the table: no crate::plugins or crate::adapters under src/kernel, no I/O crate under src/kernel or src/contracts, and no plugin importing a sibling.

Key Architectural Decisions

  • One plugin per metric, declaring everything. MetricDescriptor names the fields, their kinds, the unit, and which field becomes value; bounds() names the threshold keys; actions() names what the metric can be told to do. GET /contracts and POST /ingest are driven by the same declaration, so the catalog and the validator cannot drift.
  • Ports for every technology. The kernel holds Arc<dyn ReadingStore>, not a PgPool. The whole kernel is unit-tested against in-memory fakes with no database in sight.
  • Persist before publish. A reading reaches Postgres before it reaches Redis, so no consumer sees an event that is not yet queryable. Publishing is fire-and-forget: a broker failure is logged and never fails an ingest that already landed.
  • Threshold scope is a column, not a nesting depth. room_id NULL means building-level; a room-level row wins during resolution. Room thresholds cannot be silently dropped.
  • Device vocabulary lives behind one port. ActionDispatch takes a Command in our own vocabulary; URLs, methods and field names exist only in the dispatch adapter. See Sensor Actions & the Device ACL.
  • Authorization asks the owner. Building-to-domain lookups go to twin-service over its existing endpoint rather than into a local copy of someone else’s data; a failed lookup denies.

Integration

  • Owns telemetry-db (Postgres + TimescaleDB); no other service reads it. Retention and rollup policy in Telemetry Storage & Retention.
  • Publishes every accepted reading to Redis telemetry:raw, and every threshold breach to alerts:<metric> — alerts:temperature, alerts:peopleCount, alerts:airQuality — with no reference to whichever service consumes them.
  • Receives a threshold baseline from twin-service: over Kafka for a new building’s registration, over REST (PUT /thresholds/buildings/:id) for every later edit. Both are driving adapters over the same registration use case.
  • Exposes a self-describing metric catalog to contracts-service at GET /contracts, now including each metric’s available actions.
  • Scraped at /metrics. See Observability.
