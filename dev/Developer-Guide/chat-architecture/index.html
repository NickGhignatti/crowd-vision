Chat Service Architecture

Bounded context: Knowledge & Assistance (shared with agent) · Stack: Rust / Axum / MongoDB · Code-level walkthrough: Chat Service

The chat owns conversations: it persists message history, enforces per-conversation limits, and forwards each question to agent for an answer. It holds no assistant logic itself — agent is stateless per request and never sees a conversation until chat sends it one.

Architectural Style

Ports & Adapters, the same shape as digital-twin and notification, enforced by tests/architecture_fitness.rs. The service has exactly two things outside itself — the conversation store and the agent — so it has exactly two driven ports. domain/ is pure; service/conversations.rs holds the use cases and depends only on ConversationStore and AgentClient; the adapters supply Mongo and the agent’s SSE stream.

Components & Connectors diagram

Key Architectural Decisions

  • Conversation state lives here, not in agent. agent answers one question at a time and remembers nothing between calls; chat is what makes a multi-turn conversation possible, by sending back a bounded slice of prior messages with every question.
  • History sent to the assistant is capped, not the full conversation. Only the last HISTORY_MAX_MESSAGES messages (10 by default) are sent to agent per question — a long conversation doesn’t mean a growing prompt.
  • Hard limits everywhere a user writes. A conversation caps at 100 messages, a message at 8000 characters, a title at 120 — all rejected at the service layer before anything is persisted, not enforced by the database schema.
  • Every operation is ownership-scoped. ownedConversation checks userId and conversationId together on every read, write, and delete; a valid id for someone else’s conversation resolves to “not found,” not “forbidden,” so existence isn’t leaked either.
  • Auto-titling from the first exchange. A new conversation starts titled “New chat”; the first question becomes the title (truncated to the limit) the moment the first exchange completes, with no separate naming step.
  • Answers stream; they are not buffered. POST /conversations/{id}/messages returns Server-Sent Events — token frames as the answer is generated, then a terminal done frame carrying the saved assistant message. Total generation time is unchanged; time-to-first-token drops from seconds to milliseconds. The edge must not buffer the response (Caddy: flush_interval -1).
  • Failures split by whether the response has begun. Validation, ownership, the message cap, and an unreachable agent are all knowable before the first token, so they stay ordinary status codes. Once the stream is open the status line is gone, and a failure arrives instead as a terminal error frame on a 200.
  • Nothing is persisted until the stream completes. Tokens accumulate in memory; the exchange is written on the terminal frame and never before. An aborted generation therefore leaves no half-written answer and no retitled conversation — the conversation looks exactly as it did before the question.
  • Identity forwarded, not re-verified. the agent adapter passes the caller’s x-gateway-claims header straight through to agent — the same mesh-injected header chat itself trusted, on the same trust chain every other migrated service uses.

Integration

  • Owns chat-db; no other service reads it.
  • Calls agent’s /ask for every message, forwarding the caller’s identity — see Communication & Data Flow.
