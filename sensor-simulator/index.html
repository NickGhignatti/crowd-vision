External Simulators

CrowdVision ships two simulators that exist outside the main application cluster. They are not microservices — they are test stand-ins for systems that in production would be real external hardware or third-party services.

SimulatorLocationSimulates
Sensor Simulatorsimulators/sensor-simulator/Thermostats (temperature) and people counters (peopleCount)
Air Quality Simulatorsimulators/aq-simulator/Air-quality stations (airQuality)

Routers have no simulator: ap-simulator fakes access points for devices/ap-collector, which polls them itself and is not started from the dashboard.

Architectural Decision: Keep Simulators External

Decision: Simulators are never included in Kubernetes manifests and are not part of the production system definition.

Why: In production, CrowdVision receives data from physical IoT sensors and third-party AQ stations. Those devices are external — they know nothing about the cluster; they just POST to public API endpoints. The simulators model exactly this:

  • The K8s manifests describe only the real system — no test tooling bleeds into production configs.
  • Each simulator posts readings the same way real hardware would: to /telemetry/ingest, signed.
  • Telemetry commands a simulator the way it commands a device’s action endpoint: by a URL from its own configuration (SIMULATORS). k8s sets none, so there a start answers 404.

What Gets Simulated

Exactly the sensors placed in the digital twin. A simulator starts empty and simulates only what telemetry tells it at start.

Device kindSimulatorReading per sensor per tick
temperaturesensor-simulatorone temperature, in the sensor’s room
peopleCountsensor-simulatorone peopleCount, in the sensor’s room
airQualityaq-simulatorone airQuality, in the sensor’s room, with its own drifting state
router—nothing
  • Outdoor sensors (no room) are never simulated: readings are room-keyed.
  • Two sensors of one kind in one room give two readings for that room each tick.
  • Sync happens only at start. Sensors added, moved or removed during a run are simulated from the next start.

How It Works

  1. The dashboard’s Start simulator calls PUT /telemetry/simulation/buildings/{id} (editing role required).
  2. Telemetry reads the building’s sensors and splits them by device kind, using SIMULATORS.
  3. Telemetry POSTs each simulator /control/start with its share — an empty list when it has none, which stops that building.
  4. Each simulator ticks every 10 s and POSTs one signed batch to its TELEMETRY_INGEST_URL.

Stop (DELETE) tells every simulator to drop the building. Status (GET) is running when any simulator runs it. The browser never calls a simulator.

Control API

Called by telemetry only. The start body is pinned by schemas/fixtures/simulation-start.json, which both simulators’ tests assert.

MethodEndpointBodyEffect
POST/control/start{ buildingId, sensors: [{ sensorId, sensorType, roomId }] }Replaces what the building simulates. Empty sensors stops it. Any other key (e.g. the old targetUrl) is refused.
POST/control/stop{ buildingId }Stops the building. Stopping one it never simulated succeeds.
GET/control/status?buildingId=X—{ isRunning }

VariableDefaultPurpose
TELEMETRY_INGEST_URLhttp://gateway/telemetry/ingestWhere readings go. Set by the simulator’s own environment, never by a caller.

Running the Simulators

Both are part of the Docker Compose stack and start with just stack dev:

just stack dev --no-simulators   # skip both simulators
just stack dev aq                # skip only the AQ simulator

Standalone, against a cluster on the host (the images are built and pushed to GHCR by CD):

docker run -p 3001:3000 --add-host host.docker.internal:host-gateway \
  -e TELEMETRY_INGEST_URL=http://host.docker.internal/telemetry/ingest \
  -e TELEMETRY_INGEST_SECRET=<secret> \
  ghcr.io/nickghignatti/crowdvision-simulator:latest

Inside a container localhost is the container itself, so the ingest URL must name the host. --add-host is needed on Linux only; Docker Desktop resolves host.docker.internal by itself. Telemetry must then list the simulator’s URL in SIMULATORS to start it.

Simulation Parameters

Fixed in simulatorService.ts; change them by editing the service and rebuilding the image.

ParameterDefaultDescription
delay10000 msInterval between batches.
peopleCountRange[0, 50]Random headcount per people counter per tick.
temperatureRange[18.0, 30.0]Random °C per thermostat per tick, 2 decimals.

The air-quality simulator’s physics, scenarios and sensor-error model live in simulators/aq-simulator/ (physics.py, scenarios.py, errors.py); its tick interval defaults to 10 s.
