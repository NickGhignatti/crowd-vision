CrowdVision ships three simulators. They are not microservices: they stand in for hardware that, at a real site, sits outside the cluster.

SimulatorLocationImagePretends to be
Sensorsimulators/sensor-simulator/, Nodecrowdvision-simulatorThermostats (temperature), people counters (peopleCount)
Air qualitysimulators/aq-simulator/, Pythoncrowdvision-aq-simulatorAir-quality stations (airQuality)
Routerssimulators/ap-simulator/, Pythoncrowdvision-ap-simulatorOpenWrt routers (router), polled by devices/ap-collector

Why simulators stay outside the cluster

  • The k8s manifests describe only the real system. No test tool reaches production config.
  • Each simulator sends readings the way a real device does: signed, to /telemetry/ingest.
  • telemetry reaches a simulator through a URL in its own setting, SIMULATORS. k8s sets none, so there a start answers 404.

What is simulated

Exactly the sensors placed in the digital twin. A simulator starts empty and simulates only what telemetry sends it at start.

Device kindSimulatorEach tick, per sensor
temperaturesensor-simulatorOne temperature reading, in the sensor’s room
peopleCountsensor-simulatorOne peopleCount reading, in the sensor’s room
airQualityaq-simulatorOne airQuality reading, in the sensor’s room, with its own drifting state
routerap-simulatorNo reading: it answers ubus calls with station lists. ap-collector turns them into a Wi-Fi tick, and telemetry counts it into totalDeviceCount and ratioDeviceCount
  • Outdoor sensors (no room) are never simulated: readings are keyed by room.
  • Two sensors of one kind in one room give two readings for that room each tick.
  • Only a start syncs. A sensor added, moved or removed during a run is simulated from the next start.

Start and run

  1. A user with the right to edit the building presses Start simulator: PUT /telemetry/simulation/buildings/{id}.
  2. telemetry reads the building’s sensors and splits them by device kind, using SIMULATORS.
  3. telemetry sends each simulator POST /control/start with its share. An empty list stops that building.
  4. sensor-simulator and aq-simulator send one signed batch every 10 s to their TELEMETRY_INGEST_URL.
  5. ap-simulator only answers. ap-collector asks it, every 5 s.
StepData
1Only the building id. telemetry checks the caller may edit it
3–5{ buildingId, sensors: [{ sensorId, sensorType, roomId }] }, pinned by schemas/fixtures/simulation-start.json
6Room boxes and, when placed, router positions. A failed read answers 502
8, 9{ buildingId, readings: [...] }, signed with TELEMETRY_INGEST_SECRET
12One building’s stations per router, signed with the building’s key or TELEMETRY_INGEST_SECRET

Stop (DELETE) tells every simulator to drop the building. Status (GET) is running when any simulator runs it. The browser never calls a simulator.

Control API

Called by telemetry only. Every simulator’s tests assert the same start body.

MethodEndpointBodyEffect
POST/control/start{ buildingId, sensors: [{ sensorId, sensorType, roomId }] }Replaces what the building simulates. Empty sensors stops it. Any other key, like a URL or a coordinate, is refused
POST/control/stop{ buildingId }Stops the building. Stopping one never simulated succeeds
GET/control/status?buildingId=X—{ isRunning }

The router simulator

It fakes the routers, not their readings. Stations still travel router → ap-collector → Wi-Fi tick → telemetry, so the real counting runs on simulated data.

Routers

  • One fake router per router sensor, at /<sensorId>/ubus. Login collector / collector; any other pair is refused.
  • Probe events stream at GET /<sensorId>/ubus/subscribe/hostapd.wlan0, with the session as a bearer token, every 0.5 s.
  • The building comes from digital-twin (DIGITAL_TWIN_URL): room boxes, floors and router positions.
  • A restart drops every session. ap-collector logs in again.

People

SettingDefaultMeaning
AP_SIM_PHONES_PER_ROOM4Phones per room
AP_SIM_PASSERSBY_PER_HOUR30People walking past outside, heard through the walls
AP_SIM_PROBE_RANDOM_MAC_FRACTION1.0Share of probes sent with a random address, as phones do
  • Each phone visits 3–5 spots and stays 2–15 min at each. The next spot is on the same floor 80 % of the time.
  • Arrival is around 08:30 and leaving around 17:30, spread like a bell curve: σ 1.0 h and 1.2 h.
  • Everything is seeded by the building id: a restart walks the same people.

Signal

Path loss with walls and floors, then noise.

NumberValue
Loudness at 1 m−40 dBm
Path loss exponent2.2

Gain spread, router / phone±3 dB / ±4 dB

Example, from the defaults before noise. A phone 10 m from a router:

  • Open space: −40 − 10 × 2.2 × log10(10) = −62 dBm. It joins.
  • One wall between: −62 − 5 = −67 dBm. It still joins.
  • One floor between: −67 − 18 = −85 dBm. Too quiet to join, loud enough for its probes to be heard.

Running the simulators

The three simulators and ap-collector all start with just stack dev.

just stack dev --no-simulators   # skip the three simulators; ap-collector still runs
just stack dev --no-devices      # skip ap-collector
just stack dev aq                # skip only the air-quality simulator

Alone, against a stack on the host:

docker run -p 3001:3000 --add-host host.docker.internal:host-gateway \
  -e TELEMETRY_INGEST_URL=http://host.docker.internal/telemetry/ingest \
  -e TELEMETRY_INGEST_SECRET=<secret> \
  ghcr.io/nickghignatti/crowdvision-simulator:latest
  • Inside a container, localhost is the container itself, so the URL must name the host.
  • --add-host is needed on Linux only. Docker Desktop knows host.docker.internal already.
  • telemetry must then list the simulator’s URL in SIMULATORS to start it.

Gaps

  • sensor-simulator does not reload a code change under just stack dev: its watch rebuilds only on package.json.
