Three tools build CrowdVision. Each has one job:

ToolJobConfig
miseInstalls every language and CLI at a pinned version.mise.toml
moonRuns build, test, lint and deps per project, with cache and affected detection.moon/, each moon.yml
justThe commands a person typesJustfile, just/*.just

just is the only door for a person. just calls mise exec, and mise exec runs moon or a language tool with the pinned versions.

GitHub Actions calls the language tools directly, without moon or just, but reads the same pins. See GitHub Actions CI.

Part 1: Versions (mise)

mise installs every language and CLI CrowdVision uses, at the version pinned in .mise.toml. It puts exactly those versions on PATH for a command. One file answers “which version?” for every machine and for CI.

"ubi:moonrepo/moon" = "2.6.4"

istioctl = "1.31.3"

[env]

PinUsed forAlso read by
node = "24"frontend, sensor-simulator, eslint-configOnly the major is pinned: mise takes the newest 24, today 24.21.0
python = "3.14.8"agent, simulators, ap-collector, scripts/*.pyCI reads .python-version instead
rust = "1.99.1"The six Rust services and four schema cratesCI’s setup-rust action; cd-registry.yml builds the Rust base image with it
go = "1.27.3"The four Go services and three Go librariesCI’s setup-go action; the golang tag in the four Go Dockerfiles must match by hand

uvPython packages and virtual environments
istioctljust k8s istio-install
QUARKDOWN_VERSIONNot a tool: an environment variablejust docs build and the docs workflows compare the installed Quarkdown to it

Quarkdown is not a mise tool. Its release is a 92 MB zip with its own Java runtime, and the mise backends keep only the launcher script, which then cannot find its classes. So it is installed separately, and only its version lives here.

How a command gets its tools

Every just recipe that calls a pinned tool starts with mise exec --. Here is what that does for mise exec -- cargo --version:

StepWhat happensReal value on a developer machine
2–3mise finds .mise.toml by walking up from the current folder/home/…/crowd-vision/.mise.toml
4Each tool sits in its own folder in the store~/.local/share/mise/installs/rust/1.99.1
6Those folders go first on PATH, ahead of anything installed by hand
7Rust is handed to rustup through an environment variableRUSTUP_TOOLCHAIN=1.99.1
8–9The command runscargo 1.99.1
noteChildren inherit it: moon, then cargo, then build scriptsmise exec -- moon --version gives moon 2.6.4

Example. A laptop has Rust 1.85 from rustup as its default.

  • cargo build in a plain shell uses 1.85. A newer clippy lint present in CI does not fire.
  • mise exec -- cargo build uses 1.99.1, the same as CI.
  • which cargo can still print ~/.cargo/bin/cargo under mise exec: that is rustup’s launcher, and RUSTUP_TOOLCHAIN picks the version behind it.

Two ways to get the tools

WayWhenHow
mise exec --Recipes, scripts, anywhere a shell setup cannot be assumedWraps one command
ActivationTyping commands by handmise activate bash, zsh, fish or pwsh in the shell profile

Activation is optional. A fresh clone with only just and mise installed runs every recipe, because each one wraps its tool.

Changing a version

A version bump is its own commit, because CI reads the same numbers and lint rules can change with them.

  1. Edit .mise.toml.
  2. mise install.
  3. For Go: change the golang tag in the four Go Dockerfiles too.
  4. For Python: change .python-version too.
  5. just lint all and just test all: a new clippy or go vet can fail code that passed before.

Part 2: Tasks (moon)

moon runs the per-project tasks of the whole repository: install, build, test, lint, audit. It knows every project, skips what did not change, and replays results it already has.

Version 2.6.4, pinned in .mise.toml, always started through mise exec.

Why moon

Without itWith it
A script loops over 25 folders, one language at a timemoon run :test runs every project’s test, in parallel
Every run starts from zeroAn unchanged task is replayed in milliseconds
“Test what I touched” means remembering which folders--affected asks git
Each project repeats its build and test commandsCommands are written once per language and inherited

  • deps, relock, audit, lint-fix and every test-integration have cache: false: they change files or depend on the outside world, so a replay would lie.
  • Python’s test and lint call npm: backend/agent/package.json forwards them to uv run pytest and ruff plus pyright. Projects with no package.json replace them with uv scripts.
  • Every test lists /schemas/fixtures/**/* and /schemas/json/**/* as inputs. A leading / means “from the repo root”. Contract tests read those files, so a fixture edit must re-run them.

Real affected example. With uncommitted edits to backend/notification/CLAUDE.md, backend/chat/openapi.yaml and backend/agent/evals/dataset.json, moon query affected lists projects notification, chat and agent as touched. No test or lint is affected: none of those files is a test or lint input. Only agent:lint-fix and agent:relock are, because they declare no inputs and so match any file of their project.

Will a task run?

--force skips the cache and the affected check.

Inspecting without running

mise exec -- moon query projects            # every project, its language
mise exec -- moon query tasks               # every task of every project
mise exec -- moon task telemetry:test       # one task: command, inputs, where it came from
mise exec -- moon query affected            # what the current changes touch
mise exec -- moon query changed-files       # the files moon sees as changed

Adding a project

  1. Register it in .moon/workspace.yml.
  2. Add moon.yml with its language, and only the changes it really needs.
  3. Register it in .github/services.json too, for CI.
  4. Check: mise exec -- moon query projects.

Pick the language on purpose

The language decides the inherited tasks. javascript gives only deps and relock, for support packages. A Python project with no package.json must replace test and lint, or they fail calling npm.

Part 3: Commands (just)

just is the only command line a person needs. Every workflow is just <module> <recipe>. A recipe is a short, named wrapper around the real command, so nobody has to remember the long one.

Why just

Without itWith it
mise exec -- moon run :test --affected typed by handjust test affected
Commands kept in a README that driftsThe recipe is the command; just --list is always current
A MakefileNo file-timestamp rules to fight, readable errors, arguments and modules built in
One way per languageOne door for Rust, Go, TypeScript, Python, Docker, Kubernetes and docs

Layout

The root Justfile only declares modules and the shell:

set shell := ["bash", "-c"]
set windows-shell := ["powershell.exe", "-NoLogo", "-Command"]

mod setup 'just/setup.just'
mod stack 'just/stack.just'
mod test 'just/test.just'
mod db 'just/db.just'
mod agent 'just/agent.just'
mod docs 'just/docs.just'
mod lint 'just/lint.just'
mod k8s 'just/k8s.just'

Each module file starts with set working-directory := '..', so every recipe runs from the repo root, whatever folder just was typed in. Bare just runs just --list.

testall, affected, one per project, <svc>-integration, frontend-e2e, agent-integration, eval, integrationmoon, uv, Playwright, backend/acceptance/run-integration-tests.sh
lintall, affected, fix, workflowsmoon, scripts/check-workflow-registry.py
dbclear, clear-telemetrymongosh and psql inside the running containers

just --list <module> shows one module, like just --list k8s.

Example: just stack dev --no-agent

StepWhat happens
2Eleven scripts, each adds only the keys .env lacks: VAPID keys, eval token secret, Keycloak, Langfuse, control plane, gateway signing key, ingest key, telemetry database, Rust settings
5Root docker-compose.yml, then each folder in backend/, simulators/, devices/, then frontend/. In dev mode each folder’s docker-compose.dev.yml is added
6--no-agent is a group: it drops every name containing agent. Bare words work too: just stack dev socket drops socket
7compose.runtime.yml is generated and ignored by git. just db and just stack logs read it
9dev adds --watch, so file changes reach the containers. start uses up --build -d instead

Groups: --no-agent, --no-metrics (Prometheus, Grafana), --no-simulators, --no-devices (ap-collector). --build rebuilds images, --dry-run prints the command and stops.

Rules for recipes

  • A pinned tool always goes through mise exec --. docker, k3d, kubectl and quarkdown are not pinned and are called directly.
  • A recipe that repeats per project belongs in moon, not here. just only names it.
  • Scripts are POSIX sh or standard-library Python. No Node in scripts/.
  • Every public recipe has a [doc]. That line is the only help just --list shows.

One command, end to end: just test affected

The three tools in order. The person types one line; the rest runs underneath.

StepToolWhat happens
2–4justFinds the module, moves to the repo root (the folder above just/)
5justThe recipe body is one line, run by bash -c
6misePuts the pinned tool versions first on PATH
7–9moonPicks the affected tests, hashes them, runs or replays them
10justA line that exits non-zero stops the recipe. Later lines do not run
