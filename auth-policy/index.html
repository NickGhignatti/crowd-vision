The rules

ActionAllowed whenScopeUsed for
ReaddomainsAsStandardCustomer.contains(resource.domain)one domainAny member reads: twin buildings, telemetry readings, agent search
EditdomainsAsBusinessStaff.contains(resource.domain)one domainRename or re-domain a building, resync; telemetry writes on a building, through its edit helper
ManageDomaindomainsAsBusinessAdmin.contains(resource.domain)one domaintenancy: invite, remove another member, create subdomain, create invite code
ModelOverridemaxRoleWeight >= context.requiredWeightglobalagent: pick another model; the level comes from MODEL_OVERRIDE_MIN_ROLE
IngestDocumentsmaxRoleWeight >= 100globalagent POST /ingest
  • Read has no admin shortcut. A platform admin is not a member of every domain. To look inside one, the admin joins it.
  • .contains(), never in. In Cedar, in asks “is this entity inside that one” in an entity tree. Used on a set of strings it is always false, so every request is denied, with no error.
  • A fixed level is written in the rule (>= 100); a level an operator sets travels in context (requiredWeight).

Why roles are expanded before Cedar

Cedar cannot look up “the weight of role X”. So each service turns the membership list into flat sets before calling Cedar, and the rules only test set membership or compare numbers.

Expansion, step by step

Go accountEntity in authz.go; Rust account_entity is the same.

  1. Read the thresholds from the ladder: business_staff = 60, business_admin = 80, admin = 100.
  2. For each membership:
    1. Role not on the ladder (or, in Rust, no role at all): skip the membership entirely.
    2. Keep the highest weight seen as maxRoleWeight.
    3. Add the domain to domainsAsStandardCustomer.
    4. Weight ≥ 60: also to domainsAsBusinessStaff.
    5. Weight ≥ 80: also to domainsAsBusinessAdmin.
    6. Weight ≥ 100: also to domainsAsAdmin.
  3. Build Account::"caller" with the four sets and maxRoleWeight.
  4. Build Resource::"<domain>" with attribute domain.

Removing oneself never reaches Cedar: it is a comparison of two ids, not a rule. Any member may leave.

Global actions

ModelOverride and IngestDocuments are not tied to one domain. authorize is called with domain "", so the resource is Resource::"" (Python: Resource::"global"). The rules never read resource.domain for these two.

Example. agent with MODEL_OVERRIDE_MIN_ROLE=business_staff: can_override_model sends requiredWeight: 60. A caller whose best role is business_staff anywhere passes. A required role that is not on the ladder becomes 101, which nobody reaches.

Changing a rule

  1. Edit policy.cedar and, when needed, schema.cedarschema.
  2. Add the case to fixtures/conformance.json.
  3. Run the four replays above.
  4. A new action is a contract too: every language’s binding must learn it.

Gaps

  • agent expands roles differently in production. app/cedar_authz.py puts every domain from the claims into domainsAsStandardCustomer, whatever its role, and leaves the other three sets empty. So in agent a membership with an unknown role, or no role, still allows Read, which the conformance case “an unrecognized role … is ignored” says must deny. The Python conformance test does not catch it: it builds entities with its own correct copy, not with app/cedar_authz.py.
  • maxRoleWeight mixes domains. It is the best role in any domain, so a business_admin of one small domain passes a ModelOverride set to business_admin platform-wide. Written into the rules on purpose (global gates), but worth knowing.
  • domainsAsAdmin is built and never read. No rule uses it.
