notification is a Rust service (Axum, MongoDB, Kafka, Redis) in backend/notification. It reads breaches from Kafka and decides who should hear about each one. Then it delivers every breach twice:

  • to the bell, through Redis and socket;
  • to devices, through Web Push.

It also stores devices and preferences, and sends manual alerts.

Role in the system: Notification. Breach shape and how it is parsed: Telemetry Schema. Message shape: Notification Schema.

The idea in one minute

Imagine a fire-alarm office with a logbook.

  • A sensor tells the office: “room r1 of b1 is at 31 °C, the limit is 28”. That is a breach.
  • The office asks: which departments own building b1? (digital-twin knows). For each department it does two things: pins a note on the notice board (the bell, which every open browser of that department shows) and sends a text message to the phones of the people who asked for such alerts.
  • People choose which kinds of alerts they want, per department: temperature yes, air quality no. That is the preference.
  • If the same room keeps breaching every 10 seconds, the office does not ring every 10 seconds. After one alert it stays quiet about that room and that metric for 5 minutes. That is the cooldown.
  • A note with no department is never pinned: it would reach every department in every company.

domain/notification.rs: wording the alert

The message is built from the alert itself. The service holds no table of per-metric texts and makes no name lookup.

pub const COOLDOWN_SECONDS: u64 = 300;

pub fn notification(
    id_millis: i64, at_millis: i64, severity: Severity,
    title: &str, message: &str, domain_name: &str,
) -> Notification {
    Notification {
        id: id_millis.to_string(),
        r#type: severity,
        title: title.to_string(),
        message: message.to_string(),
        timestamp: iso8601(at_millis),
        domain_name: domain_name.to_string(),
        metric: None,
        icon: None,
    }
}

The one message that both deliveries send, for one domain. The id is the time in milliseconds as text. metric starts empty: a breach fills it in, a manual alert does not.

pub fn breach_message(alert: &AlertEvent) -> String {
    let breach = match alert.direction {
        BoundDirection::Above => " (above maximum)",
        BoundDirection::Below => " (below minimum)",
    };
    let unit = alert.unit.as_deref().map(|unit| format!(" {unit}")).unwrap_or_default();
    format!("{} : {} {} is {}{unit}{breach}",
        alert.building_name, alert.room_name, alert.label, alert.value)
}

The text is {building} : {room} {label} is {value}{ unit}{ (above maximum)}. A missing unit drops the space and the unit. A low breach ends in (below minimum).

AlertMessage

pub fn breach_cooldown_key(alert: &AlertEvent) -> String {
    format!("alert:{}:{}:{}:{}",
        alert.metric, alert.field, or_unknown(&alert.building_id), or_unknown(&alert.room_id))
}

pub fn breach_push_title(alert: &AlertEvent) -> String {
    match alert.building_name.as_str() {
        "" => format!("{} Alert", alert.label),
        building => format!("{} Alert - {building}", alert.label),
    }
}
  • The cooldown key has metric, field, building, room, so a CO₂ alert does not mute a temperature or AQI alert in the same room. An empty id becomes unknown.
  • The title is {label} Alert - {building}, or just {label} Alert when the building has no name.

impl Audience {
    pub fn of(claims: &GatewayClaims) -> Self {
        if claims.is_system() || claims.is_global_admin() {
            return Audience::Unrestricted;
        }
        Audience::Domains(claims.domains())
    }

    pub fn permits(&self, domain: &str) -> bool {
        match self {
            Audience::Unrestricted => true,
            Audience::Domains(domains) => domains.iter().any(|d| d == domain),
        }
    }
}

sub starts with system:Unrestricted

Membership does not reach down to sub-domains: a member of unibo is not, by that alone, a member of a sub-domain of unibo.

pub fn system_claims_header() -> String {
    STANDARD.encode(r#"{"sub":"system:notification-service","memberships":[]}"#)
}

When the service calls digital-twin for a breach there is no person behind the call. It presents itself with this made-up header: base64 of a claims object whose sub is system:notification-service. The name keeps its old -service suffix on purpose: it is an identity at a trust boundary, and a test pins it byte for byte. Renaming it would change a trust boundary.

The admin rule is a role check in this service, not a Cedar decision: the service does not embed the Cedar bundle. The test the_admin_role_is_the_top_of_the_shared_ladder reads backend/libs/auth-contracts/roles.json and fails if a role above admin appears.

The outcomes

pub enum BreachOutcome {

on_breach, step by step

pub async fn on_breach(&self, raw: &str) -> BreachOutcome {
    let alert: AlertEvent = match serde_json::from_str(raw) {
        Ok(alert) => alert,
        Err(e) => {
            log::error!("[Event] Failed to process alert: {e}");
            return BreachOutcome::Invalid;
        }
    };

Parse the record as the shared AlertEvent. A message that is not the shape telemetry writes is invalid, not parsed on a best-effort basis.

    if !alert.is_alertable() {
        log::warn!("[Event] No delivery path for a {} breach in building {}, dropping", alert.metric, alert.building_id);
        return BreachOutcome::Unsupported;
    }

Only the metrics in ALERTABLE_METRICS are delivered. Anything else is dropped, but counted as unsupported_metric, so it is visible and never silently skipped.

    let key = breach_cooldown_key(&alert);
    match self.cooldown.is_active(&key).await {
        Ok(true) => return BreachOutcome::Suppressed,
        Ok(false) => {}
        Err(e) => {
            log::error!("[Event] Failed to read the alert cooldown: {e:?}");
            return BreachOutcome::Failed;
        }
    }

Is the cooldown key set? Yes: Suppressed, stop. Not set: go on. Redis failed: Failed (the record will be parked, see below).

    let message = breach_message(&alert);
    let building = alert.building_id.as_str();
    let domains = match self
        .domain_directory
        .domains_for_building(building, &system_claims_header())
        .await
    {
        Ok(domains) => unique_non_empty(&domains),
        Err(e) => {
            log::error!("[Event] Failed to resolve domains for building {building}: {e:?}");
            return BreachOutcome::Failed;
        }
    };

Build the text. Ask digital-twin which domains own the building, as the system identity. Failure: Failed. unique_non_empty removes duplicates and empty names, so those never become rooms.

    let outcome = if domains.is_empty() {
        // A message with no domain would reach every tenant's browser, so it is dropped.
        log::error!("[Event] {label} alert for building {building} belongs to no domain, dropped. Alert: {message}", label = alert.label);
        BreachOutcome::Unroutable
    } else {
        self.fan_out(&message, &breach_push_title(&alert), &domains, &alert.metric).await;
        BreachOutcome::Delivered
    };

    if let Err(e) = self.cooldown.start(&key, COOLDOWN_SECONDS).await {
        log::error!("[Event] Failed to arm the alert cooldown: {e:?}");
    }
    outcome
}
  • No domain: never broadcast. Unroutable.
  • One or more domains: deliver to each (fan_out).
  • In both cases the cooldown is armed after the work, for 300 seconds. If arming fails it is only logged.

fan_out: the same message to every domain

async fn fan_out(&self, message: &str, push_title: &str, domains: &[String], metric: &str) {
    for domain_name in domains {
        let now = self.clock.now_millis();
        let sent = Notification {
            metric: Some(metric.to_owned()),
            ..notification(now, now, Severity::Danger, push_title, message, domain_name)
        };
        self.publish(&sent).await;
        self.push.to_domain(&sent, domain_name, Some(metric)).await;
    }
}

For each domain, one Notification with severity = danger and the metric filled in. It goes out twice: publish (the bell) and to_domain (devices, filtered by the metric). A failed Redis publish is only logged:

async fn publish(&self, sent: &Notification) {
    if let Err(e) = self.bus.publish(sent).await {
        log::error!("Failed to publish a notification: {e:?}");
    }
}

So a failed delivery never changes the outcome. It is still Delivered.

The cooldown

async fn is_active(&self, key: &str) -> anyhow::Result<bool> {
    Ok(self.connection.clone().get(key).await?.is_some())
}

async fn start(&self, key: &str, seconds: u64) -> anyhow::Result<()> {
    self.connection.clone().set_ex(key, "1", seconds).await?;
    Ok(())
}

A key either exists or does not. SET key "1" EX 300 makes it expire by itself after 300 seconds. Nothing else is kept in Redis for this: alerts are not stored.

The key is read first and set after delivery. Two records of the same breach handled at the same moment can both pass the read, so both deliver. See Gaps.

Worked example. telemetry reports 31 °C every 10 s from 10:00:00.

Redelivery from Kafka (after a crash) and a renamed consumer group (which replays the whole topic) are both absorbed by the same cooldown.

alert_listener.rs: reading Kafka safely

This is the most careful file in the service. The goal: never lose a breach, even if the process dies half way, and never get stuck on a record that cannot be handled.

The consumer

let consumer: StreamConsumer = ClientConfig::new()
    .set("bootstrap.servers", brokers)
    .set("group.id", GROUP_ID)             // "alerts"
    .set("auto.offset.reset", "earliest")
    .set("enable.auto.commit", "false")
    .create()?;
consumer.subscribe(&[ALERTS_TOPIC])?;
  • The group is named alerts: after what it consumes, not who consumes it.
  • earliest: a group with no committed offset reads the whole topic from the start.
  • No auto commit. Offsets advance because this service says a record is done, not because a timer fired. Without this, a crash could leave the offset past a breach that was never delivered.

Before subscribing, ensure_topics creates alerts and alerts.dlq (1 partition each) if they are missing, and ignores “already exists”. Subscribing to a topic that does not exist waits for a metadata refresh, five minutes by default.

The loop that never ends

pub async fn listen(brokers: &str, alerts: Arc<Alerts>) -> anyhow::Result<()> {
    loop {
        match consume(brokers, alerts.clone()).await {
            Ok(()) => log::warn!("[Event] Alert stream ended, reconnecting"),
            Err(e) => log::error!("[Event] Alert consumer failed: {e}"),
        }
        tokio::time::sleep(RECONNECT_DELAY).await;
    }
}

Any ending (clean or error) waits 5 seconds and starts again. A broker that is down at start is not fatal: the listener retries every 5 s.

16 at a time

consumer
    .stream()
    .for_each_concurrent(IN_FLIGHT, |message| { … })   // IN_FLIGHT = 16

Up to 16 records are handled at once. That is faster, but it means they can finish out of order: record 42 can end before 40. This creates a problem for the commit.

The watermark

Committing an offset in Kafka means “everything below this is done”. It is a line, not a list. If 42 finishes first and the service commits 42, then dies, records 40 and 41 are lost forever.

struct Partition {
    in_flight: BTreeSet<i64>,
    completed: BTreeSet<i64>,
}

fn started(&mut self, partition: i32, offset: i64) {
    self.partitions.entry(partition).or_default().in_flight.insert(offset);
}

fn finished(&mut self, partition: i32, offset: i64) -> Option<i64> {
    let state = self.partitions.entry(partition).or_default();
    state.in_flight.remove(&offset);
    state.completed.insert(offset);

    let lowest_running = state.in_flight.iter().next().copied();
    let committable: Vec<i64> = state
        .completed
        .iter()
        .take_while(|candidate| lowest_running.is_none_or(|running| **candidate < running))
        .copied()
        .collect();

    let watermark = committable.last().copied();
    for offset in committable {
        state.completed.remove(&offset);
    }
    watermark
}

Two sets per partition: offsets running and offsets done. When one finishes, take the done offsets that are lower than the lowest one still running. The highest of them is the new watermark. Only that run is committed.

Worked example. Offsets 40, 41, 42 start.

EventRunningDoneCommit

40 finishes4140, 4240, so the commit position is 41 (the next to read)
41 finishesnone41, 4242, so the commit position is 43
fn commit(consumer: &StreamConsumer, partition: i32, watermark: i64) {
    // A committed offset names the next record to read, not the last one read.
    position.add_partition_offset(ALERTS_TOPIC, partition, Offset::Offset(watermark + 1))
    // … consumer.commit(&position, CommitMode::Async)
}

The + 1 is because Kafka stores “the next record to read”.

If the service dies in between, Kafka delivers again from the last commit. The cooldown stops most of the repeats from reaching people.

What to do with a record

enum Disposition {
    Settled,
    Park(&'static str),
}

async fn handle(alerts: &Alerts, payload: Option<&[u8]>) -> Disposition {
    let Some(raw) = payload.and_then(|bytes| std::str::from_utf8(bytes).ok()) else {
        metrics::record_alert_consumed("undecodable");
        return Disposition::Park("undecodable");
    };
    let outcome = alerts.on_breach(raw).await;
    metrics::record_alert_consumed(outcome.label());

    match outcome.label() {
        label @ ("invalid" | "failed") => Disposition::Park(label),
        _ => Disposition::Settled,
    }
}
  • Not text, invalid, or failed: park it. Retrying the same record in a moment would not fix it (malformed beyond parsing, or a dependency was down).
  • Everything else: settled.
if let Disposition::Park(reason) = handle(&alerts, message.payload()).await
    && let Err(e) = park(&dead_letters, &message, reason).await
{
    // Leaving the offset uncommitted is the whole point: the
    // record is still on the topic and will be redelivered.
    log::error!("[Event] Failed to park an alert in {ALERTS_DLQ_TOPIC}: {e}");
    return;
}

Parking copies the record to the dead-letter topic with a reason header (undecodable, invalid or failed). If the parking itself fails, the function returns without marking the offset finished. So the offset is never committed past it, and Kafka delivers it again. Better a repeat than a loss.

service/push.rs: the devices

pub async fn to_domain(&self, payload: &Notification, domain_name: &str, notification_type: Option<&str>) {
    match self.preferences.accounts_subscribed_to(domain_name, notification_type).await {
        Ok(accounts) => self.to_accounts(payload, &accounts).await,
        Err(e) => log::error!("Failed to resolve subscribers of {domain_name}: {e:?}"),
    }
}

pub async fn to_accounts(&self, payload: &Notification, account_names: &[String]) {
    if account_names.is_empty() {
        return;
    }
    let subscriptions = match self.subscriptions.find_by_accounts(account_names).await {
        Ok(subscriptions) => subscriptions,
        Err(e) => {
            log::error!("Failed to load push subscriptions: {e:?}");
            return;
        }
    };
    join_all(subscriptions.iter().map(|subscription| self.deliver(subscription, payload))).await;
}

async fn deliver(&self, subscription: &WebPushSubscription, payload: &Notification) {
    if self.sender.send(subscription, payload).await == PushOutcome::SubscriptionGone
        && let Err(e) = self.subscriptions.delete_by_endpoint(&subscription.endpoint).await
    {
        log::error!("Failed to drop a dead push subscription: {e:?}");
    }
}
  1. Ask which accounts want this kind of alert in this domain.
  2. Load all of their devices.
  3. Send to every device at the same time (join_all). One slow or dead device never holds up the others.
  4. A device that answers “gone” is deleted. Any other failure leaves it in place.
Push service answersOutcomeAction
2xxDeliverednone
404 or 410SubscriptionGonedelete the subscription by endpoint
any other status, network error, 10 s timeout, encryption errorFailedlog only, keep it

A 403 means the push service refused the VAPID signature: a wrong or rotated key. Deleting on it would wipe every device at once, so it is kept.

The bell and the switches

  • The bell message goes to the whole domain room and carries metric.
  • The browser hides a breach whose metric the account switched off (isVisible in frontend/src/utils/commons/notification.ts).
  • Push applies the same rule on the server, through notificationType in step 1.
  • A manual alert has no metric: the bell always shows it.

adapters/driven/twin.rs: who owns the building?

The same lookup pattern as in Socket, with one difference in how it caches. Here is the whole of it.

const TIMEOUT: Duration = Duration::from_secs(2);
const TTL: Duration = Duration::from_secs(15 * 60);

async fn domains_for_building(&self, building_name: &str, claims_header: &str) -> anyhow::Result<Vec<String>> {
    if let Some(domains) = self.cached(building_name) {
        return Ok(domains);
    }

    let gate = self.gate(building_name);
    let _lookup = gate.lock().await;
    // Whoever held the gate may have just answered this exact question.
    if let Some(domains) = self.cached(building_name) {
        return Ok(domains);
    }

    let domains = self.fetch(building_name, claims_header).await?;
    if !domains.is_empty() {
        self.remember(building_name, &domains);
    }
    Ok(domains)
}
  1. A cached answer under 15 minutes old: return it.
  2. Else take the gate of this building. One lookup per building at a time.
  3. Check the cache again (the one who held the gate may have just filled it).
  4. Ask digital-twin. Cache the answer only if it is not empty.
let url = format!("{}/domain/{}", self.base_url, urlencoding::encode(building_name));
// … GET with the claims header; on a network error or 5xx, wait 50 to 100 ms and try once more
if !response.status().is_success() {

The building name goes through urlencoding::encode, so it cannot leave the /domain/ route. One retry on a network error or 5xx, never on a 4xx.

Registering a device: subscribe

pub async fn subscribe(State(state): State<AppState>, claims: GatewayClaims, Json(body): Json<SubscribeRequest>)
    -> Result<impl IntoResponse, DomainError>
{
    let account_name = claims.account_name();
    let supplied = match body.subscription {
        Some(subscription) if subscription.endpoint.is_some() => subscription,
        _ => IncomingSubscription { endpoint: body.endpoint, keys: body.keys },
    };
    let keys = supplied.keys.unwrap_or_default();

    let subscription = WebPushSubscription::new(
        account_name, supplied.endpoint.as_deref(), keys.p256dh.as_deref(), keys.auth.as_deref(),
    )?;
    state.preferences.register_device(&subscription).await?;

    if let Some(domain_name) = domain_of(body.domain_name, body.domain_id) {
        require_membership(&claims, &domain_name)?;
        let updates = body.preferences.resolve_lenient(account_name, &domain_name)?;
        state.preferences.apply(&updates).await?;
    }

    Ok((StatusCode::CREATED, Json(json!({ "success": true }))))
}

In order:

  1. The account comes from the claims, never from the body or the path. A body with "accountName": "mallory" sent by Ada still writes to Ada.
  2. Take the subscription from the subscription object, else from top-level endpoint and keys. Both shapes are accepted.
  3. Build and validate it (below). Store it (an upsert).
  4. If a domain is named (domainName or domainId): check membership, then switch preferences on.
  5. Answer 201 {success: true}.

  • The upsert key is the endpoint. One browser that signs in as another account moves its endpoint to that account.

Two ways to read a request

  • Lenient: for /subscribe. No type means every alertable metric. No enabled means on. Only an explicit false turns it off.
  • Strict: for POST /preferences. A missing type or enabled is a 400: the person must say exactly what to change.

How one switch is written

async fn set(&self, update: &PreferenceUpdate) -> anyhow::Result<()> {
    let owner = owner(&update.account_name, &update.domain_name);

    self.collection
        .update_one(owner.clone(),
            doc! { "$pull": { "preferences": { "notificationType": &update.notification_type } } })
        .await?;

    self.collection
        .update_one(owner,
            doc! {
                "$setOnInsert": { "accountName": …, "domainName": …, "createdAt": DateTime::now() },
                "$push": { "preferences": { "notificationType": &update.notification_type, "isSubscribed": update.enabled } },
            })
        .upsert(true)
        .await?;
    Ok(())
}

Two writes on the one document of {account, domain}:

  1. $pull any entry with this notificationType.
  2. $push the new {notificationType, isSubscribed}. upsert creates the document on the first write, and $setOnInsert sets createdAt only then.

So writing the same switch twice leaves one entry. The two writes are not atomic: a crash between them leaves the type missing, which reads as off.

apply writes updates one after the other and stops at the first error, so a list can be half applied.

It runs at every start:

fn require_membership(claims: &GatewayClaims, domain_name: &str) -> Result<(), DomainError> {
    if Audience::of(claims).permits(domain_name) {
        return Ok(());
    }
    Err(DomainError::Forbidden(format!("Not a member of domain {domain_name}")))
}

The membership check is the same Audience as everywhere else. So an admin or a system: caller may change preferences for any domain.

main.rs and configuration

Startup order:

  1. Connect to MongoDB and create the indexes. Failure stops the service.
  2. Connect to Redis. Failure stops the service.
  3. Run switch_on_new_metrics_once. Failure is logged only.
  4. Spawn the Kafka listener. A broker down at start is not fatal: the listener retries every 5 s.
  5. Serve HTTP with graceful shutdown on Ctrl+C or SIGTERM.

Gaps

  • alerts.dlq has no reader. Parked records stay there until the topic’s retention removes them.
  • The cooldown check is not atomic. Read, deliver, then set: two copies of one breach handled together both deliver.
  • A long breach alerts every 5 minutes. telemetry sends one record per breaching reading, and nothing marks the end of a breach.
  • Preference writes are two steps. A crash between $pull and $push loses that switch, which then reads as off.
  • A forbidden domain on /subscribe still stores the device. The answer is 403, which can read as “nothing stored”.
  • The owner cache and its gates are never emptied. Each building name ever looked up keeps an entry and a lock for the life of the process.
  • The push contact address is fixed in code. The VAPID sub claim is mailto:admin@kubeet.dev, with no setting to change it.
