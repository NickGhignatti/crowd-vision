Every deployable part ships as one image. Each service keeps its Dockerfile beside its code, and all images follow one of five patterns, one per language. The images are built in three places: by Compose on a laptop, by ci-docker on a pull request, and by cd-registry on master.

A release build, step by step

StepWhat happensCached when
1Start from the shared toolchainrust-base unchanged
2–3Put the service and its schema crates where ../../schemas/... points—
4Write recipe.json: every dependency and its version, no source code—
5Only the recipe enters builder, not the sourcerecipe.json byte-identical
6The schema crates go in again: they are path dependencies, and cargo needs them on disk to cookschema files unchanged
7Compile every dependency: tokio, axum, sqlx, rdkafka…Steps 5–6 unchanged: a source edit keeps this layer
8Files read only by the service’s own code, like policy.cedar, come after the cook—
9–10Compile the service itselfNever, after a source change
11–13Copy only the binary and libz.so.1, which distroless lacks—

Example. A one-line change in src/kernel/ingest.rs:

  • recipe.json comes out the same, so step 7 is cached.
  • Only steps 9–10 run: one crate compiles instead of a few hundred.

Why the schemas are copied before each cook, not only before prepare. Each stage starts from chef, with an empty /app/schemas. prepare needs the crates to read their Cargo.toml. cook needs them again to build them. A crate missing at cook time stops the build half way, with cargo failing to read /app/schemas/<crate>/Cargo.toml.

The debug stage and sccache

dev, and debug-deps where it exists, cooks under sccache:

RUN --mount=type=cache,target=/sccache,sharing=shared \
    RUSTC_WRAPPER=sccache SCCACHE_DIR=/sccache CARGO_INCREMENTAL=0 \
    cargo chef cook --recipe-path recipe.json
  • The wrapper is set on that one step, so it never reaches the release stages or the running container.
  • It helps when the cook must run again but the cache is warm: a Cargo.toml change, or a schema change. Then most crates come from /sccache.
  • It does not help a first build: the cache is empty, and sccache adds its own hashing on top.
  • sharing=shared is safe: entries are keyed by a hash of the compiler inputs and written whole.

Then dev runs a plain cargo build, with the same flags cargo run uses. A container then starts with nothing left to compile.

Traps

  • A merged pull request ships the CI image. cd-registry promotes the :pr-<sha> image when it exists, so :latest for a Go or Rust service is alpine plus the CI binary, not the distroless production stage. The CI binary is built on an Ubuntu runner: Rust links against glibc, and Go runs without CGO_ENABLED=0, while Alpine ships musl. tenancy and registry also lose their migrations/ folder. Not run here; read from the workflows.
  • just k8s build names images by hand. It lists 12 docker build lines with their own paths and contexts, separate from .github/services.json. A new service must be added to both.
  • A new path dependency means four COPY lines. One in planner, one before each cook (dev or debug-deps, builder). Missing one fails only that stage.
  • Python and Node images run as root. kube-score’s user check is switched off in ci-k8s.
  • VITE_* values are fixed at build time. Changing the backend URL needs a new frontend image, not a new environment variable.
