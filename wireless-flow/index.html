Wireless People Flow

Where people are in a building, live, from the Wi-Fi signals their phones already emit: a dot per phone on the twin, and room counts stored as metrics.

Status: phase 1 built on simulated routers; not yet tried on a real OpenWrt site. Tracks issue #314.

Applies to: devices/ap-collector, telemetry (/telemetry/observations, three router metrics), digital-twin (the estimator), socket (the devices event). No new service.

Two phases, in order

Phase 1 — routers only. Poll the access points the building already has, and listen to the probe requests they hear. Zero new hardware.

Phase 2 — dedicated sniffers. Raspberry Pi rigs in monitor mode, for devices the routers miss. Only after phase 1 is proven in a real building.

What Crosses Into CrowdVision

The Dutch DPA is explicit: “Storing multiple location points per device means that the data is not anonymous.” So the design keeps a phone’s identity on site and never stores a position.

DataWhere it existsHow long
MAC addresscollector memory onlywhile the phone is heard
Token (random, secrets.token_hex(8), never derived from the MAC)signed tick, Kafka wifi-observations, twin memory10 min on Kafka; in twin, until unseen for 3 ticks
Positiontwin memory (one per track, no history), Redis pub/sub twin:devices:{id}the current tick only
Room countsTimescale readingsthe platform’s retention (below)

Invariants:

  • No MAC leaves the site. The collector swaps every address for a minted token; nothing turns a token back.
  • No position is stored. Twin keeps each track’s current position only. Dots go out on Redis pub/sub, nowhere else.
  • A dot carries no id. twin_schema::Device refuses unknown fields, so socket drops a dot carrying a token.
  • Only counts are stored: totalDeviceCount, ratioDeviceCount, estimatedOccupancy.

This is pseudonymous personal data while it is live

A token follows one phone for as long as it stays, and Kafka holds ten minutes of them. A dot has no id, but a viewer watching a near-empty building can follow one dot from tick to tick. So a site needs a legal basis and a notice before enabling it (Wi-Fi terms, employment agreement), exactly as for any Wi-Fi analytics. Turning off probes (subscribeProbes: false) limits it to people who joined the Wi-Fi.

What Is Stored, And Why That Is Safe

A count carries no identifier and no per-device row, so there is nothing to single out. That is the whole argument for the stored data, and it is only as strong as the two conditions below.

Why Routers-Only Works

The obvious objection: MAC addresses are randomized, so won’t one phone look like a different person to every access point it passes?

No — randomization is per-SSID, not per-AP. Every AP in the building broadcasts the same SSID, so a device roaming across them keeps one address.

PlatformBehaviour on the building SSID
Android 10–15Persistent randomized MAC derived from the network profile (SSID + security type). Stable across APs, stable across forget-and-rejoin, until factory reset.
Apple (iOS 18 / macOS Sequoia)On WPA2-AES or WPA3, the private address is fixed per SSID. Only open and pre-WPA2 networks rotate — every 2 weeks.

Wi-Fi roaming requires this. The DHCP lease, L2 forwarding tables and 802.11r fast transition are all keyed on the station MAC. If it changed on roam, open TCP connections would drop and roaming would not function.

The objection is correct for the other regime

Probe-request MACs are random per scan burst and uncorrelated between listeners. So a probe address is never counted: the collector groups one address’s frames into a burst (one scan), gives the burst a fresh token, and the twin only places it.

Two regimes

RegimeWhat the AP seesRouters-only?
Associated — device joined the Wi-FiEvery frame, continuously, stable per-SSID MAC, RSSI per APYes. This is phase 1.
Unassociated — visitor never joinsSporadic probe requests, streamed by hostapd (subscribeProbes, off by default)Partly. Bursts place passing dots; counting them is phase 2.

Phase 1 covers everyone on the Wi-Fi and misses the walk-through visitor. For facility management the associated population is generally the population that matters.

It is also the only regime with a workable legal basis: a captive portal, Wi-Fi terms of service or an employment agreement supports consent or legitimate interest. Ambient sniffing of passers-by supports neither — that is what the AP fined a Dutch municipality for in 2021. That is why subscribeProbes is off by default: a site turns it on only with a basis for it.

Positions, Estimated in the Twin

Digital-twin owns the floor plan and the router placements, so it places the phones. Telemetry never sees a coordinate, and no copy of the geometry can go stale when a router moves.

How a phone is placed (service/estimator.rs, service/tracks.rs):

  • Each floor is cut into 0.5 m cells inside rooms. Each cell stores the signal every router on the floor should hear from it: −40 dBm at 1 m, path-loss exponent 2.2, 5 dB per wall.
  • A connected phone’s track is a posterior over cells: each tick weighs every cell by how well it explains the phone’s signals, and by distance from the last position (spread grows 0.5 m/s; cells beyond 2 m/s of walking are cut). A token unseen for 3 ticks is dropped.
  • A burst (one scan heard by several routers) gets a fix: the cell whose expected signals fit best. It joins a track only when exactly one connected phone explains it within 9 dB. A burst fitting none is a passing dot (connected: false); one fitting two is dropped.

Why a grid fit, not circles. Fitting circles (trilateration) needs every distance right, but walls and weak antennas only ever lower a signal, so every circle comes out too big. Measured on 470 simulated bursts: right room 95% for the grid fit, 69% for circles.

Measured on a recorded run (tests/data/wifi-recording.jsonl, 15 min, 48 phones, simulated):

DotsEach phone in its router’s room
Right room79.4%75.0%
Room counts, total off1 4621 988
Position errormedian 4.0 m, p90 8.1 m—
  • Nearly all of it comes from memory between ticks, not from bursts: linking by place almost never fires, since most bursts fit two phones on one router.
  • The simulator’s radio and scan rates are guesses; a real walk test decides the real numbers.

Fine Timing Measurement (802.11mc/az/bk) stays rejected: it is client-initiated, so the infrastructure never learns the position unless an app reports it back.

Phase 1 — Routers-Only

The collector

A small daemon on the building network. Polls each AP every pollIntervalS (10 s), holds one in-memory token table, posts one signed Wi-Fi tick per building per poll to /telemetry/observations (schemas/fixtures/wifi-observations.json). It counts nothing: telemetry counts the tick per router room.

  • Which APs: the router sensors placed in the twin, read from GET /telemetry/collector at start and every syncIntervalS (300 s). A router that stays keeps its session; telemetry unreachable keeps the previous list.
  • How to reach them: the sensor’s endpoint is the ubus URL (endpointTemplate fills a missing one); driver openwrt-iwinfo selects the iwinfo reader, anything else hostapd.
  • What it reports: the routers that answered, every connected phone each one lists (roam leftovers dropped), and the probe bursts. Every tick is posted, even one where no router answered: an empty answered tells telemetry nothing was measured, so no room gets a fresh 0. Trimmed to the contract’s limits (2000 rows, keeping the loudest; 2000 bursts, keeping the newest; 6 loudest routers per burst), since telemetry refuses an oversized tick whole. A refused or failed post is dropped, never retried: the next poll supersedes it.
  • How to log in: the collector’s own file — one site-wide ubus login and ifaces, per-router overrides. Never sent to the platform.
  • How it proves which building it is: keys: { "<buildingId>": "<device key>" } in the same file, issued by an editor (POST /telemetry/device-keys/buildings/{id}). Each key reads that building’s routers and signs its ticks; it cannot sign for another building.
  • Probes (subscribeProbes: true): one hostapd probe stream per router interface, grouped each tick into bursts (app/bursts.py) — one address within 2 s of its first frame is one scan, keeping each router’s loudest frame. A burst the tick cuts in half waits for the next tick. --dry-run prints counts, never an address or a token.
  • Tokens (app/tokens.py): every address is swapped for a random token (secrets.token_hex(8)), minted, never derived, so nothing can turn one back. A connected phone keeps its token until it is missing for 3 ticks; a burst gets a fresh one, unless it was sent from a connected phone’s own address. The mac → token table lives only in the collector’s memory.

On OpenWrt the readings come from hostapd over ubus — hostapd.<iface> get_clients returns every associated station with its signal in dBm. iw dev <iface> station dump is the equivalent without ubus.

Per tick:

  1. Collect (mac, rssi, idle) from every AP. iwinfo’s inactive is the idle time. hostapd has none: idle is how long that station’s packets.rx has not changed, so it is one poll coarse, and a station first seen counts as fresh.
  2. Drop roam leftovers. A MAC listed by several APs keeps only its least-idle rows (within 1 s: each AP is polled on its own clock read). A station associates with one AP; the old one still lists it, signal frozen, until ap_max_inactivity (300 s).
  3. Tokenise: swap every MAC for its token; group probes into bursts.
  4. Post the tick. Telemetry then counts it: one token is one phone, counted once, in its loudest router’s room.

Union by phone, never sum per-AP client counts

Summing the client lists of overlapping APs is a straight multiplication of the count, and it produces exactly the symptom people expect from MAC randomization. One token on two rows is one phone; telemetry counts it once (kernel/observations.rs).

Smoothing lives in the twin, transitions are not built

Telemetry keeps no state between ticks, so its router-room count can flip a phone between rooms each tick. Digital-twin’s tracks carry each phone across ticks, which is what smooths the dots and estimatedOccupancy. Transition counts (zoneTransition, below) are still not built.

The Platform Side

Occupancy is three metrics, not one

Telemetry stores these for every room, every tick (the factor rides on the tick as devicesPerPerson):

MetricWhat it isFrom
totalDeviceCountDevices connected, each in its loudest router’s room. A measurement.telemetry, from the tick
ratioDeviceCountDevices ÷ the site’s devices-per-person factor. An estimate.telemetry, from the tick
estimatedOccupancyConnected devices placed in the room by position. An estimate.digital-twin, Kafka estimated-occupancy

estimatedOccupancy is never mixed into totalDeviceCount: the two place a phone differently, and a dashboard can show both. It counts only rooms on a floor with a placed router, and only ticks where a router answered.

Publishing only the estimate would be the smaller change and the wrong one. The factor is a per-building guess that gets re-measured, and an estimate is only as good as the factor it was derived with. Store the raw count and a corrected factor re-derives the whole history; store the estimate alone and every past bucket is permanently wrong by whatever the old factor was off by. The measurement is also the only one of the two that means the same thing in every building, which is what makes cross-site comparison possible at all.

ratioDeviceCount is emitted only where the site actually configured a factor (useDevicesPerPerson). No factor, no estimate — an estimate silently equal to the device count is a claim about people that nobody made.

Both follow the shape of the existing peopleCount plugin (backend/telemetry/src/plugins/people_count.rs): per building and room, non-negative integer, dashboard catalog, twin overlay, agent tool.

A room’s count is its router’s, not the room’s. A router hears devices wherever they stand, across walls and floors, so the reading keyed to its room says “near this router”. The figure that means what it says is the building’s: telemetry sums the rooms at the building’s newest report and serves it at GET /telemetry/connected-devices/buildings/{id}.

One device, three metrics. The access point is what gets registered as a sensor — device kind router in telemetry’s plugins::devices(), which reports all three. Registering it once per metric would count one device three times.

None carries a threshold. A device count is an access-point capacity question, not a facility one — it breaches on a room full of laptops. And the estimates beside it are guesses, so a bound on them fires on the guess as much as on the building. Occupancy alerting stays with peopleCount, which measures people instead of inferring them.

Optional — per-AP client counts

Separate from occupancy, and useful for Wi-Fi capacity planning rather than for the twin: how many stations each AP is carrying. It needs no deduplication, unlike the zone path — a station is associated to exactly one AP at a time, so the per-AP lists cannot double-count the way overlapping RSSI coverage can.

readings is keyed (building_id, room_id, metric, ts) with no AP dimension, and ingest does not validate room_id against building_rooms. So the cheap shape is a distinct metric with the AP name in roomId:

metric = "apClients", roomId = "ap-lobby-1", value = 14

Zero migration, existing index, existing hourly rollup. The alternative — the AP name as an extra field in payload — stores fine but is not in the rollup’s group by, so it never aggregates, which is the entire point of collecting it. The cost of the cheap shape is that these rows are only distinguishable from real rooms by their metric key; every query is already metric-scoped, so it works, but it is a convention and not a constraint.

Transitions (not built)

Counts of people moving from one room to another. Digital-twin’s tracks now hold the data to derive them; nothing emits them yet. One new plugin, following the same shape:

static DESCRIPTOR: MetricDescriptor = MetricDescriptor {
    value_field: "zoneTransition",
    key: "zoneTransition",
    label: "Zone Transition",
    interface_name: "IZoneTransition",
    unit: Some("people"),
    fields: &[
        FieldSpec { name: "buildingId",     kind: NonEmptyString,  required: true },
        FieldSpec { name: "roomId",         kind: NonEmptyString,  required: true },
        FieldSpec { name: "fromRoomId",     kind: NonEmptyString,  required: true },
        FieldSpec { name: "timestamp",      kind: Finite,          required: true },
        FieldSpec { name: "zoneTransition", kind: NonNegativeInt,  required: true },
    ],
};

static BOUNDS: &[BoundSpec] = &[BoundSpec { key: "maxTransitions", field: "zoneTransition", label: "Zone transitions", unit: None, direction: Above }];

roomId is the destination; fromRoomId is the extra field, so it lands in the stored payload while the columns stay as they are — consistent with Telemetry Storage. One registration line in backend/telemetry/src/main.rs and the metric is live everywhere.

maxTransitions is not decoration: a sudden flow spike across an edge is the signal for an evacuation or an incident, and the alert path is already built.

Registration

devices/, not simulators/. A simulator is a fake you throw away; the collector is the sensor, shipped to every building and running unattended. edge/ would collide with the ingress proxy, which is what “the edge” means everywhere else in this repository.

  • ap-collector: "devices/ap-collector" in .moon/workspace.yml.
  • An entry in .github/services.json with no image key. ci-gate.yml gates the docker matrix on select(.image and (.ci != false)), so omitting the image skips the build while the tests still run. Do not copy the simulators’ "ci": false — that also drops the package from coverage and from check-workflow-registry.py, and union-by-MAC is the likeliest bug in the design.
  • A job in ci-gate.yml using tpl-python-ci.yml, listed in both docker.needs and ci-passed.needs — check-workflow-registry.py fails otherwise.
  • moon.yml overrides the inherited test / lint, which shell out to npm. Agent wraps uv in a package.json; this package cannot, because the root .gitignore ignores every package.json. Both overrides use script:, not command: — command: merges with the inherited task’s args and silently runs uv test.
  • Python, no runtime dependencies: ubus and /telemetry/observations are both JSON over HTTP, and signing is hmac.new(key, body, sha256). urllib.request covers it.

What Is Built, What Is Open

Built on branch feat/collector-bursts, against ap-simulator only:

PartWhere
Burst grouping, MAC → token, one signed tick per poll (10 s)devices/ap-collector
Tick contracttwin_schema::WifiObservations, fixtures/wifi-observations.json
Check, count per router room, republish to Kafkatelemetry POST /telemetry/observations
Estimator, tracks, accuracy testdigital-twin estimator.rs, tracks.rs
Dots to the browsertwin → Redis twin:devices:{id} → socket devices event
Room counts by positiontwin → Kafka estimated-occupancy → telemetry estimatedOccupancy

Open, and only real hardware answers them:

  • A walk test on a real OpenWrt site. The simulator’s radio model and scan rates are guesses; the measured accuracy above holds only on them.
  • Probe addresses: does a connected phone use one random address per burst (fine) or per frame (breaks grouping)? How often does it scan with the screen off?
  • Exit lag: a router lists a departed phone until ap_max_inactivity (300 s). A time limit would fix it, but would also drop phones that are present but asleep.
  • Routers with no placement add nothing to positions; a floor with none gets no dots and no estimatedOccupancy.
  • The frontend does not draw the dots yet.

The risky unknowns are physical, not code: whether signals separate two rooms depends on where the routers are mounted. Measure before tuning.

Phase 2 — Dedicated Sniffers

Only once phase 1 runs in a real building. Adds coverage of devices that never associate.

Raspberry Pi with a dual-band monitor-mode NIC (mt7612u, ath9k), roughly €60 per unit. An ESP32 is €5 but 2.4 GHz only, and modern phones probe heavily on 5 GHz — systematic undercount. Acceptable for a bench prototype, not for a building.

Do not de-randomize. The literature is good — Bleach reports ~99%, vMac and Espresso combine information elements, sequence numbers and RSSI, one IE-attribute method reports 99% precision across 70+ device types — and every one of them is re-identification engineering. It buys accuracy this feature does not need, at the one cost it cannot pay.

Count without identity instead. RateCount (2025) estimates the device count from a provably unbiased closed form over the rate at which probe frames arrive, with an error model. Learning-free: no training set, no per-site model tuning, no MAC ever inspected. The Keio scheme is the same idea — a phone emits a roughly constant probe rate, so the rate scales with the population.

This is simultaneously the lazier engineering and the defensible privacy story.

Practical corrections the estimator needs: channel hopping means only a fraction of frames are heard, so a duty-cycle term; probe rate varies by phone model and screen state.

Deployment Prerequisites

Phase 1 is only correct if the Wi-Fi is configured for it. These are requirements, not recommendations.

What is measured is devices; what a facility manager wants is people. That gap is the conversion factor above, and it is why both numbers are published separately rather than one being quietly substituted for the other. The caveat belongs in the user-facing docs too, not only here: ratioDeviceCount and estimatedOccupancy are estimates and read like facts.

The conversion rounds up. One device at a factor of 2.5 is 0.4 of a person, and rounding that to zero reports an occupied room as empty — the one fact the collector otherwise takes care to keep distinct from a genuinely empty zone. An empty zone still converts to 0.

A rejected or unreachable tick POST is logged and dropped, not raised: the run loop calls the post path directly, so an escaping error ends the collector on a single telemetry restart. One lost batch costs one poll interval of resolution; the next tick supersedes it.

Calibration

Every number that depends on the physical world is configuration, per building:

  • devices-per-person conversion factor
  • poll interval
  • the estimator’s radio model (1 m signal, path-loss exponent, wall loss); today ap-simulator’s values
  • phase 2: probes-per-device rate, channel-hop duty cycle

None of these are constants. A building full of engineers and a building full of visitors have different device ratios, and no model can see that from the code.

Two numbers are not on that list, because they are ceilings rather than tuning:

  • requestTimeoutS <= pollIntervalS (defaults 5 s and 10 s). Holds only because the collector polls every AP of a building concurrently. Polled in sequence a tick would cost the sum of its APs’ timeouts, so enough dark APs would silently slow the real poll rate. One AP’s own interfaces are still read in series, so an AP with many radios and a long timeout is the one case still worth checking by hand.

Alternative — Consume the Vendor Controller

If the building runs Cisco, Aruba or Mist, the controller already computes client positions. Cisco Spaces Location Cloud API returns cartesian (x, y) per floor; Mist is equivalent.

Zero hardware, zero algorithm — but vendor lock-in, and the vendor holds the MAC addresses. That moves the privacy problem rather than removing it, and the platform then depends on a commercial contract. Worth taking where the hardware already exists; not worth designing for.

Prior Art & References

Ordered by how directly it feeds the build. The first group is code to read before writing any; the research groups are there to justify — or overturn — a decision, not to be reimplemented.

Phase 1 — closest existing implementations

Read these first. Every one solves a piece of the collector.

  • vjt/openwrt-ha-presence — the closest analogue. Scrapes RSSI from every OpenWrt AP and assigns each device to a room by strongest signal. This is phase 1’s algorithm, already written, at single-home scale.
  • awilliams/wifi-presence — Go daemon on the AP itself, subscribing to hostapd’s control interface for client connect/disconnect events rather than polling. Worth reading for the event-driven alternative to a poll loop.
  • WiFi Presence Detection for Home Assistant Using OpenWrt — end-to-end walkthrough. Enables the wifi_stations collector in prometheus-node-exporter-lua, then polls /metrics on each AP every 5 s for wifi_station_signal_dbm. The simplest transport for the collector: no ubus auth, no custom ACLs.
  • [HOWTO] Reliable WiFi presence for Home Assistant using OpenWrt hostapd events — the practical failure modes of naive presence detection. Read it for what goes wrong, not for the architecture.
  • FUjr/homeassistant-openwrt-ubus — working ubus client pulling per-station RSSI, connection quality and which AP interface each device is on.

Phase 1 — the ubus / hostapd surface

  • OpenWrt hostapd ubus interface (source) — authoritative definition of get_clients and the rest. The docs lag; the source does not.
  • ubus (OpenWrt micro bus architecture) — techref — the JSON-RPC-over-HTTP protocol: session.login for a token, then call with the object and method.
  • OnionIoT — ubus tutorial (part 3 covers rpcd) — the clearest walkthrough of exposing and calling ubus methods remotely.
  • Easy ubus daemons with rpcd (Freifunk) and ubus service development with rpcd (Zilogic) — needed if the collector ends up running on the AP.
  • openwrt-ubus-rpc (PyPI) — Python client that already wraps login and get_hostapd_clients.
  • OpenWrt forum — UBUS over HTTP for WiFi presence detection — the ACL file under /usr/share/rpcd/acl.d/ needed to grant hostapd methods to a non-root RPC user. Easy to miss; nothing works without it.
  • Home Assistant — OpenWrt (ubus) integration — documents the exact router-side setup (rpcd, uhttpd-mod-ubus, ACL) in user-facing terms.

Trilateration — reference implementations

Circles lost to the grid fit on simulated data (69% vs 95% right room); listed so the comparison is checkable.

  • ifindev/indoor-positioning-algorithms — trilateration and min-max in Python over RSSI from four routers.
  • dvalenza/Trilateration-Example — minimal three-signal position solve.
  • WiFi Trilateration With Three or More Points — the least-squares generalisation, and the path-loss model d = 10 ^ ((Ptx - RSSI) / (10n)) whose exponent n is the per-site calibration that makes this expensive.
  • Indoor Positioning and Tracking in a Multi-Level Residential Building Using WiFi (MDPI) — accuracy actually achieved in a real multi-floor building.

Phase 2 — sniffers and probe capture

  • schollz/howmanypeoplearearound — counts probe requests over a window via tshark on a monitor-mode adapter. Small, readable, and the direct ancestor of the rate-based approach.
  • GiovanniBaccichet/openwrt-multi-sniffer — an OpenWrt AP sniffing probe requests across multiple channels in both 2.4 and 5 GHz. Bridges phase 1 and phase 2 hardware: it may remove the need for separate Pi units entirely.
  • fdd4s/wifi-analytics — captures MAC and RSSI from monitor mode; a worked presence-analytics pipeline.
  • ETS-PoliTO/esp32-sniffer — reference ESP32 firmware for probe-request capture.
  • SensorsIot/Wi-Fi-Sniffer-as-a-Human-detector — companion code to the video below.
  • Building an ESP32 packet sniffer (HackMag) — monitor-mode walkthrough, and the 2.4 GHz-only limitation stated plainly.
  • Kismet, monitor mode, wardriving on OpenWrt (forum thread) — Kismet is fully passive and handles channel hopping, logging and device tracking already. Viable as the capture layer under a custom estimator.

Phase 3 — device-free CSI sensing

Not planned. Tracked because it removes the identifier problem entirely.

  • espressif/esp-csi — official CSI support, including a wifi_sensing_demo for motion and human presence with on-site training.
  • ESP32 CSI Toolkit — extracts CSI from an ESP32 in active or passive mode.
  • Wi-ESP CSI Tool — alternative toolkit.

Counting and localization research

  • RateCount: Learning-Free Device Counting by Wi-Fi Probe Listening (arXiv 2507.03873) — the phase 2 estimator. Unbiased closed form over probe arrival rate; no training, no MAC inspected.
  • MAC address randomization tolerant crowd monitoring (arXiv 2112.02161) — Vision and TrueSight; also uses data and beacon frames, not probes alone.
  • Indoor crowd estimation using the number of Wi-Fi probe requests (Keio) — the constant-probe-rate assumption RateCount formalises.
  • Signals from the Crowd: Uncovering Social Relationships (IMC 2013) — the origin of large-scale probe analytics, and a blunt demonstration of what this data reveals when it is not aggregated. Read it as a privacy argument.
  • MAC Address Anonymization for Crowd Counting (arXiv 2009.09876) — why salted hashing is not anonymisation, with collision-rate requirements.
  • MAC address de-randomization for WiFi device counting (ScienceDirect) — the approach deliberately rejected.
  • Efficient Association of Wi-Fi Probe Requests under MAC Randomization — vMac (INFOCOM’21) — likewise: state of the art in the direction not taken.

Datasets and simulation

For validating an estimator before any hardware exists.

  • CRAWDAD sapienza/probe-requests (IEEE DataPort) — the classic set: four one-shot events of 40 min to 6 h, plus six weeks of fixed capture on a campus.
  • Labelled device Wi-Fi probe requests (Mendeley, 2024) — 22 devices in 6 modes each. The only public set where the emitting device is labelled, so it is the only one that can score an estimator’s error.
  • Dataset of Wi-Fi Probe Requests (arXiv 2308.04435)
  • WiFiSim: simulating Wi-Fi probe requests via AOSP analysis (arXiv 2509.15501) — generate synthetic probe traffic with realistic device behaviour. Useful for testing before a Pi exists, in the same spirit as simulators/.
