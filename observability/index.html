Who exposes what

All six use the Rust prometheus crate.

ServiceMeasures
telemetrytelemetry_ingest_total, persist failures, publish outcomes, telemetry_http_*
digital-twinhttp_requests_total, http_error_requests_total, http_request_duration_seconds
notificationSame three names
chatchat_http_*
dashboardtelemetry_fanout_latency_ms, events in and out
socketMessages relayed, skipped, connections refused, clients connected

No metrics at all: agent, claims-gateway, tenancy, registry, provisioner.

HTTP metrics label the route template, never the real URL, so ids cannot explode the series.

Local vs cluster settings

Each environment has its own Prometheus and Grafana: compose starts one pair locally, the cluster runs another. Only one pair runs at a time. Their settings differ:

Alert rules

AlertFires when
ServiceDownA target stops answering
TwinServiceHighErrorRate, ChatServiceHighErrorRate, SensorServiceHighErrorRateOver 5% errors
TwinServiceHighLatency, ChatServiceHighLatency, SensorServiceHighLatencyp95 over 1 s
ContractsServiceFanoutLatencyHighp95 fan-out over 500 ms
SensorIngestPersistFailuresReadings fail to save
SensorIngestStalledNo accepted reading in 10 min
SensorTelemetryFanoutFailingPublishing fails

The queries name no job, so one rule set fits both stacks. They work because a metric name normally belongs to one service.

Trap: in the cluster digital-twin and notification share metric names, so the Twin rules really add up both services.

Gaps

  • Nobody gets told. No Alertmanager, so an alert only shows on Prometheus’s page.
  • Rules are copied by hand between the two stacks, and have drifted: the cluster still has NodeEventLoopLagHigh, for Node services that no longer exist.
  • Local misses notification: it is not in prometheus.yml.
  • No alert yet on socket’s relay_messages_skipped_total or socket_connections_rejected_total, nor on notification’s dead-letter topic.
  • Control plane is invisible: a failing sign-in shows nowhere.
