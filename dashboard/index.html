dashboard is a Rust service (Axum, Tokio, MongoDB, Redis) in backend/dashboard. For the role and the choices behind it, read Dashboard architecture.

It does two unrelated jobs in one process:

Column preferences and the catalogHTTP, api/DashMap, /contracts of other servicesDashMap, MongoDB

The idea in one minute

Imagine a big shared radio. Every building in the system talks on one channel, all mixed together: telemetry:raw.

  • A person watching building b1 does not want to hear b9. And the browser does not want to filter a firehose.
  • So dashboard sits in the middle, as a switchboard. It listens to the mixed channel, looks at the building name on every message, and re-broadcasts the message on that building’s own channel: telemetry:filtered:b1.
  • It only does this for buildings it knows. A building with no saved columns is dropped on the floor.
  • The other job is a small notebook: for each building, which columns should the table show? The notebook lives in memory (fast) and is copied to MongoDB (so it survives a restart).

state.rs and models.rs: the shared notebook

#[derive(Clone)]
pub struct AppState {
    pub building_preferences: Arc<DashMap<String, Vec<String>>>,
    pub mongo_col: Collection<PreferenceDocument>,
}

AppState is what every handler and the tunnel share.

  • building_preferences maps a building id to its column names, for example "b1" -> ["roomName", "temperature"]. DashMap lets many requests read and write at once. Arc lets all of them hold the same one.
  • mongo_col is the handle to the MongoDB collection.
  • #[derive(Clone)] means copying an AppState is cheap: the Arc just adds one more owner, it does not copy the map. A test confirms it: a clone sees what the original inserts.
#[derive(Debug, serde::Serialize, serde::Deserialize)]
pub struct PreferenceDocument {
    #[serde(rename = "_id", skip_serializing_if = "Option::is_none")]
    pub id: Option<mongodb::bson::oid::ObjectId>,
    pub building_id: String,
    pub allowed_columns: Vec<String>,
}

One MongoDB document per building. MongoDB wants the key _id, so rename maps the Rust field id to it. skip_serializing_if = "Option::is_none" means “when id is None, leave _id out”, so MongoDB makes one itself when it first stores the document.

pub use telemetry_schema::{MetricContract, MetricsDiscoveryResponse};

The catalog types are not defined here. They come from the shared telemetry-schema crate, the same one telemetry uses to build its /contracts answer. This is on purpose: once, the field names in two copies drifted apart and the catalog came back empty at runtime. With one shared definition, drift is a compile error.

db.rs: three small functions

pub async fn connect(uri: &str) -> anyhow::Result<Collection<PreferenceDocument>> {
    let opts = ClientOptions::parse(uri).await?;
    let client = Client::with_options(opts)?;
    let col = client
        .database("crowdvision")
        .collection::<PreferenceDocument>("preferences");

    // Unique index: enforces one document per building at the database level.
    let index = IndexModel::builder()
        .keys(doc! { "building_id": 1 })
        .options(IndexOptions::builder().unique(true).build())
        .build();
    col.create_index(index).await?;

    Ok(col)
}

The database name crowdvision and the collection name preferences are fixed in code. A name inside MONGO_URI is ignored. The unique index says “two documents may not share a building_id”, so the database itself blocks duplicates. Creating an index that already exists does nothing, so this is safe on every start.

pub async fn load_all(
    col: &Collection<PreferenceDocument>,
) -> anyhow::Result<Vec<PreferenceDocument>> {
    let cursor = col.find(doc! {}).await?;
    Ok(cursor.try_collect().await?)
}

find(doc! {}) is “match everything”. try_collect drains the cursor into a Vec. An empty collection gives an empty Vec, not an error.

pub async fn upsert_preference(
    col: &Collection<PreferenceDocument>,
    building_id: &str,
    allowed_columns: &[String],
) -> anyhow::Result<()> {
    let document = PreferenceDocument {
        id: None,
        building_id: building_id.to_string(),
        allowed_columns: allowed_columns.to_vec(),
    };
    let filter = doc! { "building_id": building_id };
    col.find_one_and_replace(filter, document)
        .upsert(true)
        .await?;
    Ok(())
}

“Replace the document of this building, or create it if there is none” (upsert(true)). The whole document is replaced, so the stored columns are always exactly the last list sent.

claims.rs: who is asking

impl<S: Send + Sync> FromRequestParts<S> for GatewayClaims {
    type Rejection = StatusCode;

    async fn from_request_parts(parts: &mut Parts, _state: &S) -> Result<Self, Self::Rejection> {
        let raw = parts
            .headers
            .get(CLAIMS_HEADER)
            .and_then(|value| value.to_str().ok())
            .ok_or(StatusCode::UNAUTHORIZED)?;
        let payload = ClaimsPayload::decode(raw).ok_or(StatusCode::UNAUTHORIZED)?;
        if payload.user_id().is_none() {
            return Err(StatusCode::UNAUTHORIZED);
        }
        Ok(GatewayClaims { payload })
    }
}

This makes GatewayClaims an Axum extractor: put it in a handler’s arguments, and Axum runs this code first. If it returns an error, the handler never runs and the caller gets that status.

  1. Read the header x-gateway-claims (CLAIMS_HEADER, from the shared claims-schema crate). Missing or not text: 401.
  2. Decode base64 (standard or URL-safe) JSON into ClaimsPayload. Fails: 401.
  3. No sub: 401.
  4. Otherwise the claims are stored in the struct.

Every route except /metrics and /health takes it. But look at the field: #[allow(dead_code)] pub payload. Nothing ever reads the payload after this check. Any signed-in person can read or change any building’s columns. See Gaps.

Reading and saving columns

Reading

pub async fn get_preferences(
    _claims: GatewayClaims,
    Path(building_id): Path<String>,
    State(state): State<AppState>,
) -> impl IntoResponse {
    match state.building_preferences.get(&building_id) {
        Some(columns) => (
            StatusCode::OK,
            Json(GetPreferencesResponse {
                building_id,
                allowed_columns: columns.clone(),
            }),
        )
            .into_response(),
        None => StatusCode::NOT_FOUND.into_response(),
    }
}

The handler’s arguments are its inputs, and Axum fills them in order. _claims is the check from above (the leading underscore says “I need it to run, but I do not use it”). Path is the {building_id} from the URL. State is the shared notebook.

Look the building up in memory. Found: 200 with the columns. Not found: 404. MongoDB is never asked.

Saving

pub async fn update_preferences(
    _claims: GatewayClaims,
    State(state): State<AppState>,
    Path(building_id): Path<String>,
    Json(payload): Json<UpdatePreferencesRequest>,
) -> impl IntoResponse {
    let column_count = payload.allowed_columns.len();

    state
        .building_preferences
        .insert(building_id.clone(), payload.allowed_columns.clone());

    let col = state.mongo_col.clone();
    let bid = building_id.clone();
    tokio::spawn(async move {
        if let Err(e) = db::upsert_preference(&col, &bid, &payload.allowed_columns).await {
            log::error!("Failed to persist preference for {bid}: {e}");
        }
    });

    let response = UpdatePreferencesResponse {
        status: "success".to_string(),
        building_id,
        active_columns: column_count,
    };

    (StatusCode::OK, Json(response))
}

In order:

  1. Json(payload) is an extractor too: it reads and checks the body as {"allowed_columns": [...]}. A body that is not that shape is refused by Axum before the handler runs.
  2. Put the new list in the DashMap now. Readers see it at once.
  3. tokio::spawn starts the MongoDB write in the background and moves on. If it fails, the only trace is a log line.
  4. Answer 200 right away. active_columns is the count (3), not the list.

The edge strips /dashboard (handle_path in the Caddyfile), so /dashboard/preferences/b1 arrives as /preferences/b1.

StepData
1{"allowed_columns":["roomName","roomMaxOccupancy","temperature"]}
4DashMap["b1"] = ["roomName","roomMaxOccupancy","temperature"]
6active_columns is 3
7MongoDB {_id, building_id:"b1", allowed_columns:[…]}, one document per building
  • 200 does not mean saved. The answer goes out before the MongoDB write runs. If the write fails, or the pod stops between the two, the change lives only in memory and is lost at the next restart.
  • The list is not checked. An empty list, an unknown name or a duplicate is stored as sent.
  • GET reads only the DashMap.

Starting columns

const DEFAULT_COLUMNS: &[&str] = &["roomName", "roomMaxOccupancy"];

pub async fn init_building_preferences(
    _claims: GatewayClaims,
    Path(building_id): Path<String>,
    State(state): State<AppState>,
) -> StatusCode {
    let mut is_new = false;
    state
        .building_preferences
        .entry(building_id.clone())
        .or_insert_with(|| {
            is_new = true;
            DEFAULT_COLUMNS.iter().map(|s| s.to_string()).collect()
        });

    if is_new {
        let defaults: Vec<String> = DEFAULT_COLUMNS.iter().map(|s| s.to_string()).collect();
        let col = state.mongo_col.clone();
        tokio::spawn(async move {
            if let Err(e) = db::upsert_preference(&col, &building_id, &defaults).await {
                log::error!("Failed to persist init preference for {building_id}: {e}");
            }
        });
    }

    StatusCode::OK
}
  1. entry(…).or_insert_with(…) is one atomic step: “if this building has no entry, run the closure and store what it returns”. The closure runs only when the key is missing, and sets is_new = true on the way.
  2. A new building gets roomName and roomMaxOccupancy, and the same fire-and-forget MongoDB write as a save.
  3. A building that already had columns is left alone, and nothing is written.

Calling it twice is safe: the second call finds the entry and does nothing.

digital-twin calls it after a building registration, and only when its sync_enabled is on. A failed call is logged there as failed to init building preferences, and nothing retries it.

A building with no columns gets no live feed

The tunnel drops every tick for a building missing from the DashMap. If the init call above fails, the building shows no live data until someone saves its columns once.

The catalog

The column picker needs to know which metrics exist. dashboard does not know: it asks the services that do.

pub fn discover_services() -> Vec<String> {
    let mut services = vec![];
    for (key, value) in std::env::vars() {
        if !key.ends_with("_METRICS_URL") {
            continue;
        }
        services.push(value);
    }
    services
}

Look at every environment variable. Each one whose name ends in _METRICS_URL is a source, and its value is the address. Today: SENSOR_METRICS_URL=http://telemetry:3000 and TWIN_METRICS_URL=http://digital-twin:3000, in both compose and Kubernetes. A new source is a new variable, not a code change.

async fn collect_metrics(services: Vec<String>) -> Vec<MetricContract> {
    let client = match reqwest::Client::builder()
        .timeout(Duration::from_secs(2))
        .build()
    {
        Ok(c) => c,
        Err(e) => {
            error!("Failed to build HTTP client: {e}");
            return Vec::new();
        }
    };

    let fetches = services.into_iter().map(|service| {
        let client = client.clone(); // cheap: Arc clone, shares the pool
        async move { fetch_service_metrics(&client, &service).await }
    });
    let per_service: Vec<Vec<MetricContract>> = join_all(fetches).await;

    let mut possible_metrics: Vec<MetricContract> = Vec::new();
    for metrics in per_service {
        for metric in metrics {
            push_unique_metric(&mut possible_metrics, metric);
        }
    }
    possible_metrics
}
  1. One HTTP client with a hard 2 second timeout per request. Without a timeout, a hung service would hang the whole page, with no error.
  2. join_all runs all the fetches at the same time. The total wait is about the slowest one, not the sum.
  3. Merge the answers one after another (the merge depends on order), skipping duplicates.
async fn fetch_service_metrics(client: &reqwest::Client, service: &str) -> Vec<MetricContract> {
    let url = format!("{service}/contracts");
    let res = match client.get(&url).send().await {
        Ok(res) => res,
        Err(e) => {
            error!("Failed to reach {url}: {e}");
            return Vec::new();
        }
    };
    match res.json::<MetricsDiscoveryResponse>().await {
        Ok(MetricsDiscoveryResponse::ServiceContract(sc)) => sc
            .metrics
            .into_iter()
            .map(|mut m| {
                if m.source.is_none() {
                    m.source = Some(sc.service.clone());
                }
                m
            })
            .collect(),
        Ok(MetricsDiscoveryResponse::Metrics(metrics)) => metrics
            .into_iter()
            .map(|mut m| {
                if m.source.is_none() {
                    m.source = Some(service.to_string());
                }
                m
            })
            .collect(),
        Err(e) => {
            error!("Failed to deserialize metrics from {url}: {e}");
            Vec::new()
        }
    }
}

One source, three outcomes. Unreachable or slow: log it, return an empty list. Not parseable: log it, return an empty list. Parseable, in one of two accepted shapes:

  • An object {"service": "telemetry", "metrics": [...]}: any metric without a source gets the service name.
  • A bare list [...]: any metric without a source gets the URL.

Either way every metric ends up with a source, so the picker can say where it comes from.

fn push_unique_metric(possible_metrics: &mut Vec<MetricContract>, metric: MetricContract) {
    if possible_metrics.iter().any(|existing| {
        existing.kind == metric.kind
            && existing.interface == metric.interface
            && existing.source == metric.source
    }) {
        return;
    }

    possible_metrics.push(metric);
}

Two metrics are “the same” when kind, interface and source all match. Then the second one is skipped. Six metrics with two duplicates give four.

  • The catalog is fetched on every request. Nothing is cached.
  • A failed source never fails the request: the answer is 200 with fewer metrics. The only trace is the log line.

Example. digital-twin hangs. After 2 seconds its fetch gives up. The client gets 200 with the metrics of telemetry only, and the log says Failed to reach http://digital-twin:3000/contracts.

For the shapes and parsing rules, see Telemetry Schema, the metric catalog.

The tunnel

The core of the second job. It starts as a background task and then lives forever.

Opening the connections

pub async fn start_telemetry_tunnel(redis_url: &str, state: AppState) {
    let client = match redis::Client::open(redis_url) {
        Ok(c) => c,
        Err(e) => {
            info!("Failed to create Redis client: {}", e);
            return;
        }
    };

    // Connection for Subscribing
    let pubsub_conn = match client.get_async_pubsub().await {
        // … on error: log and return
    };

    // Connection for Publishing
    let publish_conn = match client.get_multiplexed_async_connection().await {
        // … on error: log and return
    };

    tokio::spawn(async move {
        listen_and_fanout(pubsub_conn, publish_conn, state).await;
    });
}

Two connections, on purpose. In Redis, a connection that has subscribed to a channel can do nothing else. So one connection only listens, and a second one publishes. The publishing one is multiplexed: many tasks can use clones of it at the same time.

If any step fails, the function logs it and returns. It does not panic and it does not retry.

The hot loop

async fn listen_and_fanout(
    mut pubsub: redis::aio::PubSub,
    publish_conn: MultiplexedConnection,
    state: AppState,
) {
    if let Err(e) = pubsub.subscribe(RAW_CHANNEL).await {
        info!("Failed to subscribe to {}: {}", RAW_CHANNEL, e);
        return;
    }
    let mut stream = pubsub.on_message();

    // Hot loop: Awaits raw telemetry
    while let Some(msg) = stream.next().await {
        let payload: String = match msg.get_payload() {
            Ok(p) => p,
            Err(_) => {
                continue;
            }
        };

        let envelope: TelemetryEnvelope = match serde_json::from_str(&payload) {
            Ok(envelope) => envelope,
            Err(e) => {
                info!("Raw telemetry is not a tick envelope, skipping: {e}");
                continue;
            }
        };

        let state_clone = state.clone();
        let pub_conn_clone = publish_conn.clone();

        // Spawn a Tokio task for the fan-out.
        // This ensures the ingestion stream is NEVER blocked by processing time.
        task::spawn(async move {
            process_and_publish(envelope, payload, state_clone, pub_conn_clone).await;
        });
    }
}
  1. Subscribe to RAW_CHANNEL (the name comes from telemetry-schema, never typed twice).
  2. For each message, in the loop:
  3. Read it as text. Not text: skip silently.
  4. Parse it as a TelemetryEnvelope. Not a tick: log it and skip.
  5. Hand the work to a new task and go straight back to waiting. A slow publish can never hold up the next message.

Notice what is passed on: the parsed envelope (to decide where it goes) and the original payload text (to send).

Where does it go?

fn resolve_channel(
    envelope: &TelemetryEnvelope,
    building_preferences: &DashMap<String, Vec<String>>,
) -> Option<String> {
    if !building_preferences.contains_key(&envelope.building_id) {
        info!(
            "No preferences found for building {}, skipping",
            envelope.building_id
        );
        return None;
    }

    // No metric filtering: every sensor metric a known building emits is forwarded;
    // which columns the dashboard displays is a client concern.
    Some(envelope.channel())
}

A pure function: given a tick and the notebook, return the channel to publish on, or None to drop. A building that is not in the notebook gets None. A known building gets envelope.channel() (from the shared crate), which is telemetry:filtered:{buildingId}. The tick can only ever land in its own building’s channel.

Despite the name of the old design, there is no metric filter. Every metric of a known building goes through. The saved columns only decide what the table shows, in the browser.

Publishing

async fn process_and_publish(
    envelope: TelemetryEnvelope,
    payload: String,
    state: AppState,
    mut publish_conn: MultiplexedConnection,
) {
    metrics::EVENTS_RECEIVED.inc();

    let Some(channel) = resolve_channel(&envelope, &state.building_preferences) else {
        return;
    };

    // The tick is relayed exactly as telemetry published it: a reading's
    // fields belong to whichever plugin produced them, and re-serialising here
    // would put this service in the way of a shape it has no business knowing.
    let _: redis::RedisResult<()> = redis::cmd("PUBLISH")
        .arg(&channel)
        .arg(payload)
        .query_async(&mut publish_conn)
        .await;

    let ingested_at = envelope.ingested_at_ms;
    let now_ms = std::time::SystemTime::now()
        .duration_since(std::time::UNIX_EPOCH)
        .map(|d| d.as_millis() as i64)
        .unwrap_or(ingested_at);
    metrics::FANOUT_LATENCY_MS.observe((now_ms - ingested_at).max(0) as f64);

    metrics::EVENTS_PUBLISHED.inc();
}
  1. Count one received tick.
  2. Pick the channel. None: stop (the tick is counted as received, not as published).
  3. PUBLISH the original text, byte for byte. The tick is not parsed into readings and written out again. Each reading’s fields belong to whichever plugin made them, and dashboard has no business knowing them. It needs the building id to route, and that is all.
  4. Measure how long the tick took since telemetry stamped it (ingestedAtMs), and record it. .max(0) stops a clock that runs a little behind from making a negative number.
  5. Count one published tick. The result of PUBLISH is ignored: a failed publish is not logged, and still counts as published.

Example. Three messages arrive: a tick for b1 (has columns), a tick for b9 (no columns), and the text hello.

How can the unit tests of the handlers run without MongoDB? The MongoDB driver connects lazily: building a Collection handle opens nothing. And the write is fire and forget, so the handler never waits for it. The test sees the in-memory change and ignores the failed background write. moon.yml pins test to cargo test --lib, so just test all passes with nothing running.

Gaps

  • No access check per building. Any signed-in person can read or overwrite any building’s columns. The claims are decoded and then dropped.
  • A saved column can be lost. 200 comes before the MongoDB write, and a failure is only logged.
  • No delete. A removed building keeps its entry in MongoDB and in memory, and its ticks keep being forwarded.
  • The tunnel never reconnects after a Redis restart, and a failed PUBLISH is neither logged nor counted as a failure.
  • Columns are not validated. An empty list or a name no service reports is stored as sent.
