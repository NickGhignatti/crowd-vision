Locally the whole platform runs under Docker Compose. No single file lists every service: each service keeps its own compose file beside its code, and a small script joins them into one on every start.

  • Why per service. A service is added or removed without touching a central file, and its compose file moves with it.
  • No custom networks. No file declares networks:, so every container of a project joins Compose’s default network and reaches the others by service name: telemetry:3000, redis:6379.
  • backend/agent holds 9 services: agent, agent-db, agent-ingester and the Langfuse stack (langfuse-web, langfuse-worker, langfuse-db, redis-langfuse, clickhouse, minio).

Why include: and not several -f flags

With -f a.yml -f b.yml, Compose resolves every relative path against the first file’s folder. build.context: ../.. in backend/telemetry/docker-compose.yml would then point two levels above the repo root. include: resolves each file against its own folder.

A pair of files is one entry because two separate entries may not define the same service: Compose stops with a conflict.

  2. No other service name contains chat, so nothing else goes.

Example of a trap. just stack dev db drops every service with db in its name: twin-db, telemetry-db, keycloak-db… and the stack cannot start.

A gated request

StepData
1Cookie: authentication_token=eyJhbGciOiJSUzI1NiIs…
3extractToken reads Authorization: Bearer … first, then the cookie
4Signature checked against claims-gateway’s own public key; only RS256 accepted
8{"sub":"ada","memberships":[…],"exp":…} as standard base64
10Path /twin/buildings becomes /buildings

Why the edge checks once: the services behind it never verify a signature; they read the header. The cluster does the same with Istio, so a service runs unchanged in both places: Kubernetes & Istio.

gateway lists five services in depends_on with required: false: it starts even when they are left out, and finds them when they appear, because Caddy looks up each name per request.

.env: what just stack env writes

Every dev and start runs env first. Each script appends only what is missing, so a second run changes nothing except RUST_VERSION.

ScriptWrites
create.shAn empty .env, mode 600
vapid.shVAPID_PUBLIC_KEY, VAPID_PRIVATE_KEY, VITE_VAPID_PUBLIC_KEY, a P-256 key pair; checks the lengths 87 and 43
token.shEVAL_JWT_SECRET, 32 random bytes, local evals only
config.shBACKEND_PORT=80, FRONTEND_PORT=8080, DEV_URL=http://localhost; asks for OPENROUTER_API_KEY
langfuse.shLangfuse keys, salt, passwords
keycloak.shKEYCLOAK_ADMIN_PASSWORD, KEYCLOAK_DB_PASSWORD, empty Google client fields
controlplane.shINTERNAL_SIGNING_SECRET, TENANCY_DB_PASSWORD, REGISTRY_DB_PASSWORD
gateway-key.shsecrets/gateway-dev-key.pem, a 2048-bit RSA key, only if missing
ingest-key.shTELEMETRY_INGEST_SECRET, TELEMETRY_DEVICE_MASTER_KEY
telemetry-db.shTELEMETRY_DB_PASSWORD
rust.shRUST_VERSION, rewritten every run so a bump in .mise.toml reaches the build

The RSA key is kept on disk, not regenerated: a new key would make every signed-in cookie invalid.

Live reload

LanguageWatch ruleOn a source changeOn a dependency change
Rustsync ./srccargo watch -x run rebuilds the service crate onlyCargo.toml, Cargo.lock: rebuild the image
Gosync ./air rebuilds and restartsgo.mod: rebuild
agentsync ./appuvicorn --reloadpyproject.toml: rebuild
frontendsync ./srcVite dev server, npm run devpackage.json: rebuild
  • Rust has no target/ volume. The dev image already holds a fresh build; a volume over target/ would hide it, and every dependency change would compile twice.
  • Go shares two volumes across the four services: go-mod-cache (/go/pkg/mod) and go-build-cache (/root/.cache/go-build). Go locks inside the cache folders, so four containers can use them at once.
  • Mongo runs with --wiredTigerCacheSizeGB 0.25. Without it each of the four instances may grow towards half the host’s memory.

Acceptance: just test integration

backend/acceptance/run-integration-tests.sh writes compose.integration-tests.runtime.yml:

Included fileGives
docker/rust-base/docker-compose.ymlThe Rust build image
backend/acceptance/docker-compose.infra.ymlredis, kafka
backend/{telemetry,socket,dashboard}/docker-compose.ymlThe three real services
backend/acceptance/docker-compose.integration.ymlStubs for digital-twin and claims-gateway (nginx), the real Caddy gateway, and the integration-tests runner
  • The real Caddyfile is mounted, so backend/acceptance/edge/ tests the edge that ships.
  • Stub claims-gateway answers /verify with a fixed 401 and a marker, so a test can tell an edge refusal from a service one.
  • It generates the telemetry keys itself, so it runs without just stack env.

Traps

  • just stack dev does not rebuild by default. Only --build, or a watched rebuild file, rebuilds an image. A Dockerfile change needs --build.
  • --no-simulators leaves telemetry’s SIMULATORS list as is. Starting a simulation then fails to reach them.
  • A root service cannot leave by folder. prometheus, grafana, keycloak go only by name, which is why --no-metrics exists.
  • container_name is global. ambitwin-socket is shared by the dev stack and the acceptance stack; the acceptance script removes a stopped one, never a running one.
  • Renaming a volume empties the service. Compose names the real volume after project and key: see Naming.
