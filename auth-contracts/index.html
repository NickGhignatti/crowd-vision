Go module at backend/libs/auth-contracts. It holds three things every Go service must agree on:

FileHoldsWhy shared
claims.goStandardClaims, MembershipThe shape of the caller, same in every service
roles.go + roles.jsonRoleWeights, Can()One ranking of roles, read by every language

Standard library only: no outside dependency. registry and provisioner need the signature code but never check a token, so this module must not pull in JWT libraries.

1. StandardClaims

Shape

{"sub":"8f1c2e3a-4b5d-4e6f-9a1b-2c3d4e5f6a7b","accountName":"mario",
 "sid":"b2a9c1d0-1234-4e6f-9a1b-2c3d4e5f6a7b",
 "memberships":[{"domain":"unibo","role":"standard_customer","externalId":"eppn:mario@unibo.it"}]}
JSONGo fieldMeaning
subSubAccount id. Every access decision keys on it
accountNameAccountNameName shown to people
sidSIDSession id. signer.Sign makes a new UUID when empty
membershipsMembershipsList of {domain, role, externalId}
externalIdMembership.ExternalIDThe identity provider’s id for this membership. Left out of JSON when empty

The type has no field for a tier or an identity provider. A direct sign-up and a federated one reach every service in this same shape.

2. The role ladder

Data

roles.json, embedded in the binary with //go:embed:

RoleWeight
admin100
business_admin80
business_staff60
standard_customer10
  • Read once at start-up into RoleWeights. Invalid JSON makes the program panic at start: a service never runs with a broken ladder.
  • Embedded at build time, so a running Go service cannot read a different file than the one it was built with.

How Can(have, need) decides

CallWeightsResultWhy
Can("admin", "business_admin")100 ≥ 80trueHigher passes
Can("business_admin", "business_admin")80 ≥ 80trueEqual passes
Can("standard_customer", "business_admin")10 ≥ 80falseLower fails
Can("not-a-role", "standard_customer")unknownfalseUnknown caller role denies
Can("business_admin", "not-a-role")unknownfalseA typo in the required role denies. Reading it as weight 0 would let everyone through

Where the ladder is read

One file, five readers, no copy. Changing a weight changes every language at the next build or start.

3. Internal signatures

Some calls carry no person: provisioner setting up a new organization acts for nobody, so there is no claims header to forward. These calls prove who sent them with an HMAC over the body.

The rule

  • Header: X-Signature.
  • Value: lowercase hex of HMAC-SHA256, key = shared secret (INTERNAL_SIGNING_SECRET), message = the exact request body bytes.
  • An empty body is signed too: a GET signs zero bytes.
  • Verify compares with hmac.Equal, which takes the same time whatever the input, so timing leaks nothing.

Who signs, who checks

CallerFunctionRoute on the receiverBody
provisioner registryclientSign(secret, nil)GET /internal/organizations/pending on registryempty
provisioner registryclientSign(secret, raw)POST /internal/organizations/{id}/status on registryJSON
provisioner tenancyclientSign(secret, body)POST /internal/domains on tenancyJSON
claims-gateway tenancyclientSign(secret, nil)GET /internal/memberships?accountId=… on tenancyempty
claims-gateway tenancyclientSign(secret, body)POST /internal/provision on tenancyJSON

registry also has POST /internal/organizations/{id}/suspend behind the same check.

A signed call end to end

Data at each step

Example from the shared fixture schemas/fixtures/internal-signature.json: secret an-internal-secret-that-is-at-least-32-bytes.

StepData
1Body {"buildingId":"bldg-1","status":"ready"} (40 bytes)
3Signature bd3ae57b5d5672d04b5c376ddd2b2fe60a348a9c5d151d631d6fd38241772418
4Header X-Signature: bd3ae57b…2418, same 40 bytes as body
6Those 40 bytes in memory
7A new reader over the same 40 bytes, so the handler can read them
9Recomputed signature, equal to step 3
11Handler sees the original body

A body with one extra space gives a different signature, so step 9 fails with 403.

Why each check gives its status

CaseStatusWhy
No X-Signature403Not a known service
Body cannot be read400The connection broke. Saying 403 would tell the caller its secret is wrong when it is not
Wrong signature403Wrong secret, or the body changed on the way

Gaps

  • The signature covers the body only. Method, path and time are not signed. Every empty-body GET with one secret has the same signature, so a captured one works on any GET /internal/* route behind that secret, forever.
  • Go does not check the secret’s length. telemetry refuses a key under 32 bytes; the Go services accept any non-empty INTERNAL_SIGNING_SECRET.
  • RoleIn, CanIn, Tenants have no caller. RoleIn keeps the first match, while tenancy’s own roleIn keeps the highest. Two answers to one question.
