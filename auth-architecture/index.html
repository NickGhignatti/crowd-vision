Realises the Identity & Access domain. Four Go services plus Keycloak. Code-level pages: Claims Gateway, Tenancy, Registry, Provisioner.

Who does what

PartJobKeeps
KeycloakChecks the passwordPeople
claims-gatewayTurns a Keycloak sign-in into the internal passNothing
tenancyOrganizations, memberships, invites, access rulesPostgreSQL
registryTakes a new customer’s signupPostgreSQL
provisionerTurns a signup into a working organizationNothing

Each part does one job. Signing in and signing up change for different reasons, so they live in different services.

Solid: sign-in. Dotted: signup. registry and provisioner have no route at the edge: they are reached only from inside the network.

Inside each service

All four have the same shape: a core with the rules, and adapters around it.

  • Ports only on the way out. The core says “I need a store”, and a database or a fake fills it. Tests run with no database.
  • No port on the way in. Each route has one real caller, so the handler calls the core directly.
  • provisioner has a timer instead of HTTP handlers.

Signing in

  • Memberships are read once per sign-in, never per request.
  • A first sign-in creates the membership, not the registration. So no single write has to touch Keycloak and tenancy together.
  • Example. Ada’s Keycloak token names organization northfield, and she has no membership yet.
    • northfield is open to its sign-in server: Ada joins as a customer and gets a pass with it.
    • northfield is invite-only: tenancy refuses, and Ada still signs in, with no organization on her pass.
    • northfield does not exist in tenancy: sign-in fails with 503.

Every later request

The edge checks the pass once. Services behind it trust the result.

  • Only claims-gateway ever checks a signature. Every other service reads the header and moves on.
  • Same header both ways, so a service runs unchanged locally and in the cluster.

How long a session lasts

FactValue
Pass lifetime15 min
client renews itEvery 10 min, with no user action
Renewing needsA pass that is still valid
A renewal that cannot reach the gatewayRetried after 30 s, so a short restart costs nothing
Any other request refused with 401Ends the session at once: home, and a banner offering sign-in again

Example. Ada signs in at 09:00. The pass is renewed at 09:10, 09:20, and so on, all day. Her laptop sleeps from 10:05 to 10:30, and the pass dies at 10:20. On wake-up the renewal answers 401: the app drops the session, goes home, and the banner asks her to sign in again.

Keep 10 below 15

The two numbers live in different services, and nothing checks one against the other. A pass shorter than the renew interval ends every session.

Access rules

  • tenancy is the only Go service that runs Cedar. claims-gateway only identifies people. registry and provisioner work on organizations, which the rules do not cover.
  • digital-twin, telemetry and agent run the same rules, from the same shared bundle.

Roles are flattened before Cedar runs. Cedar can test “is this in the list”, but not “is this role higher than that one”. So tenancy first turns each membership into lists:

Ada’s membershipLists she ends up in
Staff in NorthfieldVisitor or higher: Northfield. Staff or higher: Northfield

A rule then only asks “is this organization in the staff-or-higher list”.

“in” does not mean “in the list”

In Cedar, in means “is a child of”, for entities. On a plain list it denies everything, with no error. Lists need “contains”. Only the shared tests that run real rules catch this.

Two checks stay outside Cedar, because they are not about roles:

  • A person leaving an organization: is the target the caller?
  • Auth turned off in dev and test: a setting, not a rule.

Signing up

  • The customer does not wait for the creation. A signup shows “provisioning” for up to one round.
  • A repeat is safe: an organization that already exists counts as success.
  • Who may join: anyone known to the customer’s own sign-in server, if the customer brought one. Invite only otherwise.
  • No organization stays provisioning: each one ends ready or failed. A failed one is never tried again.

Choices

ChoiceWhy
Keycloak for every customerOne sign-in path, whatever the customer’s size
One pass shape, frozen in a shared packageEvery service reads it the same way
Rules run inside each serviceNo network call per decision
Organization in registry, tenant in tenancyBilling and access change for different reasons, and are not always one to one
Signup by loop, not by callCreating an organization is slow, and nobody should wait for it

Gaps

  • Only shared customers. Dedicated and on-premises signups end failed: no code builds them.
  • No customer-owned sign-in per organization, and no self-service enterprise signup.
  • Signup cannot be reached. registry takes a signup, but no edge route and no service calls it.
  • A new organization has nobody in charge. provisioner creates the organization only, with no first admin, so nobody can invite the first member.
  • A failed organization stays failed. Nothing tries it again.
  • A missing organization blocks sign-in. A Keycloak token naming an organization tenancy does not know gives 503, every time.
  • Only the first organization counts. A person in two Keycloak organizations is provisioned in the first only.
  • A pass cannot be taken back. It lives its 15 minutes; nothing checks a revoked session.
  • Internal signatures can be replayed. The HMAC covers the body only, not the method, path or time. Every internal GET with an empty body has the same signature, valid forever, for any accountId in its query.
  • agent flattens roles its own way. It puts every organization in the lowest list whatever the role, so its decisions can differ from the shared test cases. See Auth Policy.
  • A screen offline over 15 minutes stays signed out. client keeps no Keycloak refresh token, so it cannot sign in again alone.
  • No metrics from any of the four services: a failing sign-in shows nowhere.
  • Code vs domain: the domain has three roles. The code has four, with admin on top.
